# 面试手册

先讲产品和一次任务，再展开机制与取舍。面试官应能从回答中判断：你理解了哪些实现、亲自做了哪些判断、证据支持到什么范围。准备时结合[模块卡](modules.md)、[实验手册](labs.md)和[个人记录](workbook.md)，不要把参考回答当作已完成的个人经历。

## 90 秒项目介绍

以下是项目事实稿。个人贡献段需要按真实经历填写：

> PrivateAgent 是使用自备 API Key 的本机 AI 编程工作台，可以理解项目、修改代码、执行验证并审阅差异。前端使用 Vue 和 TypeScript，Tauri 管理桌面生命周期与系统能力，Python 本机执行器负责业务编排，共享 AgentRuntime 推进模型和工具循环。SQLite 保存会话、执行事件和上下文，密钥通过系统凭据库管理。
>
> 项目的重点是控制执行过程、核对交付结果。模型提出工具操作，程序按工具契约、任务限制、路径、审批状态和文件版本决定是否执行。长任务有上下文预算、取消、恢复和纠错机制；最终回答还要结合文件、命令与需求证据。项目文件在本机，推理所需内容仍可能发送给供应商。
>
> 项目采用 AI 辅助开发。我实际参与【模块／问题】，由我判断的取舍是【决策】，通过【复现／测试】验证【结果】，目前明确的限制是【限制】。

准备三版：30 秒只讲用途与核心链路，90 秒补执行控制和个人贡献，3 分钟加一个案例。用录音核对时长；若超时，删去技术栈罗列，保留调用链和个人判断。

个人经历尚未形成时，可以说：“我系统阅读并复现了其中的【机制】，能够解释【边界】，目前还没有把它用于真实供应商／用户任务验收。”这比虚构“独立设计整个系统”更可信。

## 回答组织方式

深入回答采用：**问题 → 当前实现 → 选择理由 → 失败处理 → 验证证据 → 局限**。通常先用 30 秒给主干，追问后再补字段、调用顺序和测试。

例如：“审批与版本检查解决不同问题。审批说明用户允许这个操作，文件版本说明预览依据是否仍成立。当前补丁在预览和执行之间绑定摘要、作用域并复核文件。版本变化时拒绝旧写入，重新读取和生成预览。L07 可以观察用户改动被保留；它证明被测的冲突边界，不证明任意多文件修改都有全局事务。”

## 技术追问与参考回答

### Q01 Agent 与普通聊天有什么区别

**问题：**一次回答是否足以完成任务？

**当前实现：**模型根据上下文返回工具调用或候选最终回答。`AgentRuntime` 调用 dispatcher，把工具结果按 call ID 回填，再调用模型。运行时检查步骤、工具次数、时间预算与取消；审批等待可暂停，候选回答再走本机完成验证。

**选择理由：**把决策与执行分开，使循环可替换模型、工具和事件接收方，也能统一终止条件。

**失败处理：**可恢复工具错误返回模型；未注册工具不执行；不合法回执、预算耗尽或取消走明确终止路径。

**证据：**[M06](modules.md#m06-agent-循环与本机适配)、[L01](labs.md#l01-agent-循环)。

**局限：**循环正确不代表模型规划正确；真实任务质量依赖模型、上下文和验证覆盖。

**追问：**如果模型一次提出三个工具，但只剩两次工具预算，为什么不先执行两个？

### Q02 为什么分共享核心与本机执行器

**问题：**怎样避免运行时直接耦合桌面、文件系统和特定供应商？

**当前实现：**共享核心通过 `ModelClient`、`ToolDispatcher`、`EventSink` 和取消契约推进循环。本机 `Runtime` 与 `LocalRunAdapter` 注入模型、工具、上下文、持久化和验证；Rust 提供桌面宿主与系统能力，Vue 管理视图和连接。

**选择理由：**核心算法能用合成依赖验证，本机执行器集中处理操作边界。相比把所有逻辑写在 UI 或核心类里，依赖关系更容易解释和测试。

**失败处理：**事件落库失败不能装成正常进展；本机恢复和文件问题由相应层报告，核心不自行绕过执行权限。

**证据：**[架构说明](architecture.md)、M02–M06、L01/L04。

**局限：**接口边界增加类型、版本和跨层错误映射成本。当前只保留本机桌面链，不能把共享接口说成已经部署了多种运行环境。

### Q03 如何控制文件修改与命令执行

**问题：**模型提出操作后，谁负责判断允许执行？

**当前实现：**依次核对工具可见性与 schema、用户任务限制、项目／工作区身份、路径保护、审批状态、文件或脚本版本；命令普通入口继续使用 Windows AppContainer。最终执行前还有守卫，不能只靠模型提示词。

**选择理由：**提示词影响模型选择，程序和 OS 提供实际边界；审批记录也必须有具体操作与作用域。

**失败处理：**参数不合法、越界、过期审批或不支持的沙箱能力拒绝执行；没有静默降级到更宽权限。

**证据：**[M09–M12](modules.md#m09-工具契约与按需发现)、L06–L08。

**局限：**`full_access` 不等于管理员；项目可信命令另有审批。当前没有域名级网络隔离，路径保护对未来新建敏感文件的边界也有限。

**追问：**操作通过审批但 workspace 或规则版本变了，原批准是否还能用？

### Q04 审批后文件又变了怎么办

**问题：**预览被批准后，执行依据可能已经过期。

**当前实现：**读取生成版本，补丁预览与内容摘要、路径、工作区及授权绑定。执行前再核对文件事实；中间不一致时拒绝旧补丁。多文件过程记录 journal，回滚也检查后续用户编辑。

**选择理由：**保留用户更新，比基于过期预览覆盖更重要。自动三方合并可改善部分冲突，但需要额外冲突语义和再次确认。

**失败处理：**外部修改、摘要篡改、第二个写入失败或回滚目标变化都保留已发生事实，不宣称整个过程“完全没写过”。

**证据：**[M10](modules.md#m10-文件搜索与补丁)、[L07](labs.md#l07-补丁版本冲突与局部失败)。

**局限：**文件系统没有覆盖任意多文件的数据库式全局事务；进程崩溃和回滚冲突仍可能需要人工核对。

### Q05 并发与追加指令怎么保证不会串状态

**问题：**旧模型、并行读、写工具和新要求可能同时到达。

**当前实现：**相邻合格只读工具有界并行，上限 2；写操作形成顺序屏障。工作区租约约束同一根目录的任务竞争。`RunControls` 的目标版本使旧响应失效，计划用版本避免旧更新；前端 generation 拒绝旧连接回调，事件序号处理重放。

**选择理由：**只读并发减少等待，同时避免扩展成无界任务；版本比“总是相信最后到达响应”更可靠。

**失败处理：**取消回收所有活动读；追加指令使旧调用结果不能被当成当前任务决策；已有副作用的事实仍保留。

**证据：**L06、L11、L03。

**局限：**只读契约要求执行器与外部工具声明可信；未知副作用不能因为版本变化而消失。当前没有独立只读子任务功能。

### Q06 上下文太长如何处理

**问题：**保留历史和规则会超过模型窗口。

**当前实现：**`LocalContext.prepare` 组装整个请求并预算规则、原始约束、计划、历史、工具定义等内容。可选记忆先让出预算；历史按完整调用组压缩，摘要保留必要任务状态与 source refs，原文可以续读。供应商原生状态要按格式与模型路由条件使用。

**选择理由：**直接截断最后 N 条会丢早期限制或拆开工具调用；分层保留能说明哪些内容必须留下。

**失败处理：**无法在硬限制内构造合法请求时明确失败；缺失工具结果标记 unknown，不能补造成功或直接重放。

**证据：**[M13](modules.md#m13-规则与上下文管理)、L09/L10。

**局限：**摘要有信息损失，预算估算也依赖模型与消息协议，不能承诺任意长任务无损。

**追问：**为什么“只算用户消息 token”不足以控制窗口？

### Q07 记忆系统如何实现

**问题：**哪些跨会话信息值得保存和召回？

**当前实现：**长期记忆使用独立 SQLite、作用域、来源、版本及遗忘记录。当前召回是关键词匹配与有界选择，包含中文片段、英文和路径等线索；可选内容受条数与 bytes 预算约束。使用已有记忆与自动生成分开控制，生成依据 source/version 核对过期。

**选择理由：**本机关键词实现容易审计和删除，成本较低；可以先验证来源和控制流程，再考虑语义检索。

**失败处理：**生成期间来源改变会丢弃结果，模型超时不删除原来源；记忆挤占窗口时先移除可选内容。

**证据：**[M14](modules.md#m14-长期记忆)、L10。

**局限：**同义词和隐含语义召回有限，当前不是向量 RAG；记忆可能过期，需要和当前源码或用户输入核对。

### Q08 断线、暂停、取消与崩溃如何恢复

**问题：**用户看到失联不一定说明操作没有发生。

**当前实现：**事件续读按 run ID 和 after sequence 重放；创建去重按请求身份查询。任务继续或关联恢复需要检查点、工作区、版本、模型条件、租约和原预算。进程中断后未确认的命令／外部写入记录为 unknown，旧授权不直接沿用。

**选择理由：**把观测恢复与执行恢复分开，避免为补一个响应重复执行写操作。

**失败处理：**检查点损坏、模型能力变化、预算耗尽或工作区有冲突时拒绝恢复；未知副作用先核对，不自动重放或按旧 PID 重新接管。

**证据：**[M15](modules.md#m15-任务恢复)、L03/L11。

**局限：**本机请求去重不能保证外部服务恰好执行一次；外部系统缺少幂等键或查询接口时需要人工确认。

### Q09 怎样确认任务真的完成

**问题：**模型说“完成”、计划打勾、命令返回 0 都不足以证明所有要求成立。

**当前实现：**`LocalCompletionVerifier` 核对原始需求与限制、文件事实、当前绑定的命令证据和配置的检查；证据不足给出结构化反馈，允许受原预算约束的纠错。`Observer` 记录步骤与独立检查；运行结束状态和目标验收结果分开。

**选择理由：**把可核对事实与自然语言声称分开，交付中能明确未验证项。

**失败处理：**拒绝审批不能通过重试绕过；unknown 不自动重放；重复失败、无进展与预算耗尽终止纠错。

**证据：**[M16](modules.md#m16-完成验证与纠错观察)、L05/L12。

**局限：**有限证据不能自动证明任意行为语义、用户体验或性能。用户禁止测试时要尊重限制并报告未验证。

### Q10 多模型兼容难在哪里

**问题：**不同供应商对消息、工具和流式终态有不同契约。

**当前实现：**内部规范化消息和工具调用，适配器转换 OpenAI Chat/Responses、Claude、Ollama 协议；核对工具参数、call ID、流结束、用量、能力声明和原生续接状态。协议与 API 格式需要明确配置。

**选择理由：**统一上层循环，差异集中在 adapter；原生状态保留减少不必要转换，但要防止跨路由复用。

**失败处理：**缺失终态、非法 JSON、能力不支持或续接状态被篡改时拒绝；重试只针对明确可重试错误，并考虑是否已发布公开增量。

**证据：**[M05](modules.md#m05-模型协议与适配)、L02。

**局限：**协议兼容与真实模型质量是两回事；供应商接口变化需要重新验证，不用合成回归宣布真实模型验收成功。

### Q11 Skills、文档 MCP 与通用 MCP 怎么接入

**问题：**外部工具配置、模型可见性和实际调用权限不能混为一谈。

**当前实现：**skills 按项目显式启用和版本加载。MCP 配置及凭据可属于个人，但工具按项目绑定与发现，保存 schema／版本并在调用前重新核对；stdio 需可信直接可执行文件，HTTPS/OAuth 使用相应凭据边界。文档工具与通用 MCP 的入口和能力分别检查。

**选择理由：**按需工具减少 schema 成本，项目作用域限制无关服务；OS 凭据库避免密钥进入导出文档。

**失败处理：**配置、schema、凭据或项目授权变化时拒绝旧调用；外部写入响应丢失保留 unknown，不盲目重试。

**证据：**[M17](modules.md#m17-skills-与-mcp)、L06/L13。

**局限：**本地 SDK 和 OAuth state 测试不能证明第三方真实授权、权限或数据写入安全。

### Q12 草稿、附件与队列为什么能保留失败输入

**问题：**发送确认晚到，可能覆盖新编辑；排队失败也可能丢材料。

**当前实现：**草稿带 revision、mutation/request identity，提交被核实后确认消费旧版本。附件正文与引用分离，消息和草稿保留各自归属；队列持久化输入、材料和模型条件，满足状态时推进。清理先预览引用，执行时再校验。

**选择理由：**把“用户仍拥有的输入”与“已确认创建运行”分开，失败可继续处理。

**失败处理：**旧确认不清空新输入；运行失败、重启或模型待确认保留队列内容；引用未释放时不删仍需要的材料。

**证据：**[M19](modules.md#m19-草稿附件与数据恢复)、L13。

**局限：**媒体处理受格式、大小和模型视觉能力限制；发送去重不代表所有外部副作用恰好一次。

### Q13 应用备份如何避免损坏或错误恢复

**问题：**导出 JSON 的合法性与可恢复性不同。

**当前实现：**备份格式 `privateagent.backup.v2` 使用白名单 payload 与摘要，合法 v1 仍可读；有大小、版本、材料摘要和预览 digest 校验。下载保留原始 bytes。导入映射到指定目录、新建记录，重复导入复用结果，数据失败回滚。模型按供应商、协议、API 格式、地址及模型 ID 匹配，不明确时 pending。

**选择理由：**摘要发现损坏和预览后变化；原始下载保持数值表示；模型待确认避免悄悄采用当前默认配置。

**失败处理：**超限、损坏或未知版本在写入前拒绝；写入 pending 失败回滚数据导入。配置、凭据保存和历史回滚有各自边界。

**证据：**[M19](modules.md#m19-草稿附件与数据恢复)、L14。

**局限：**应用备份不复制项目代码、API Key、活动审批、进程或长期记忆库；摘要校验不是数字签名。

### Q14 Git diff 与运行修改记录有什么区别

**问题：**如何证明哪些变化属于 Agent，而哪些来自用户或其他过程？

**当前实现：**开始任务记录 Git／文件基线，运行内保留补丁与执行事实；审阅另取当前 Git 净差异。worktree 与交接核对目录、版本、活动租约、来源和目标，冲突保留源工作区。

**选择理由：**当前 diff 表达的是与 Git 基线的最终差异，运行记录表达曾发生的操作，二者用途不同。

**失败处理：**用户脏修改、后续编辑或过期预览不能被回滚覆盖；未知进程／租约导致不安全交接拒绝。

**证据：**[M20](modules.md#m20-git-工作区与交接)、L11/L13。

**局限：**本地远端跟踪引用不证明远端实时状态；临时 Git 测试不证明真实远程协作成功。

### Q15 桌面构建与更新怎么证明可用

**问题：**源码正确、打包成功和真实安装可用属于不同验收。

**当前实现：**共享契约生成 Python/TypeScript 类型，前端构建，Python 执行器打包为 sidecar，Rust/Tauri 构建桌面宿主并生成安装产物；更新源及签名按发布契约校验。

**选择理由：**协议同步防止前后端 drift，分阶段检查便于定位。

**失败处理：**协议不一致、宿主版本不符、安装包或更新签名无效明确失败；不通过关闭验签来交付。

**证据：**[M02](modules.md#m02-桌面启动与私有-ipc)、L04、[发布说明](../releases/v1.0.1/github-release.md)。

**局限：**Tauri updater 签名用于更新可信性，Windows Authenticode 用于可执行文件发布者身份和完整性，两者不是同一个验签。历史发布证据不能替代本人当前安装、缩放与更新测试。

### Q16 AI 写了代码，你贡献了什么

使用真实案例回答：

> 我使用 AI 辅助实现【明确范围】。首先由我确认【用户约束与验收条件】，然后我沿【入口→关键依赖】定位【原因】。我比较了【方案 A/B】，选择【方案】是因为【理由和代价】。我亲自执行【命令／复现】，观察【关键断言与结果】。AI 帮助了【产物】，由我负责核对【决策与验证】。目前未验证【边界】。

准备面对三层追问：你能否不看源码画链路？如果条件改变怎么处理？能否找到测试或差异证明结论？

只有阅读和复现时，使用“我阅读并复现”“我核对了”，不要使用“我设计／修复／上线”。没有实测不填性能提升、用户数或真实调用成功率。

## 三个可复现案例

下列是候选练习，**不是已经完成的个人贡献**。先运行并记录，再决定用于“学习复现”还是“实际开发经历”。

### 案例一：预览批准后文件已被修改

**场景：**模型提出修改 A，用户审阅预览后，又在编辑器更改 A。旧批准继续写入会覆盖后续修改。

**定位链：**Repository 的读取版本→PatchService 的预览→审批绑定→执行前核对→journal／回滚。以 L07 中外部修改与第二次写入失败用例为证据。

**复现记录：**

1. 写下预览时的文件 bytes、version 与 patch ID。
2. 在用例注入的时点观察外部改动。
3. 核对执行拒绝原因与最终文件，证明用户后续内容仍在。
4. 对局部失败另列已发生写入、未发生写入和回滚状态。

**取舍：**当前拒绝过期依据。自动三方合并有可用性收益，但需要确认合并后的语义和新预览；强制覆盖缺乏对用户修改的保护。

**限制：**不能由一个测试推导任意崩溃都完整回滚。面试重点是解释版本检查怎样贯穿操作，而不只是说“加了锁”。

### 案例二：创建成功但响应丢失

**场景：**Python 已创建 run，前端没有收到响应。用户重试可能创建第二个任务。

**定位链：**草稿请求身份→useRunStream.startRun→API 创建／只读核对→Store 的幂等记录→快照与 after sequence→runProjector。L03、L13 的草稿与首会话创建测试支持不同层次。

**复现记录：**

1. 在测试中让创建响应丢失，记录实际 create 调用次数。
2. 观察客户端先只读查询，确认已存在任务。
3. 输入未变的显式重试沿用请求 ID；输入改变或终态后新提交使用新的身份。
4. 对事件断线另记录游标、缺口补齐和旧 callback 被拒绝，不把这一步当成重新执行任务。

**取舍：**请求身份与事实核对增加状态管理，但比不加区分地重新创建更安全。客户端去重和服务端去重需要配合。

**限制：**这不是外部命令或 MCP 的恰好一次保证。外部副作用可能已发生但无回执，应标记 unknown 并核对。

### 案例三：JSON 重新序列化破坏备份摘要

**场景：**后端导出含 `0.0` 的备份，前端解析为对象再 stringify，数值变成 `0`。文件仍是合法 JSON，但导入摘要不匹配。

**定位链：**[备份导出与加载](../../src/private_agent/storage/backups.py)→[历史编码](../../src/private_agent/storage/history.py)→[前端原始下载](../../apps/desktop/src/api/backups.ts)→L14 的原始字节与模型恢复用例。

**复现记录：**

1. 比较原文件与重新序列化文件的数值表示。
2. 区分 payload 摘要和整包 bytes 的预览摘要，定位是哪一层校验失败。
3. 核对原始 bytes 可以加载、改写文件被拒绝；下载路径保留原始 Blob。
4. 再观察模型条件不匹配进入 pending，而不是直接套用新默认模型。

**取舍：**原始下载简单保留协议数据；若要统一跨语言规范化，需要完整定义数值和编码契约并处理旧格式。学习复现不改变既有备份格式。

**限制：**摘要用于完整性核对，不证明备份来源可信，也不等于更新数字签名。数据往返成功不证明真实凭据恢复或供应商可用。

## 模拟面试与评分

D28 使用下列流程，录音并填写[评分记录](workbook.md#模拟面试记录)：

1. 90 秒介绍，不看稿。
2. 10 分钟架构展开，必须画一次工具调用。
3. 20 分钟追问：任选四个 Q01–Q15，再追问一个失败场景和 Q16。
4. 10 分钟回放：逐句标记源码事实、执行证据、推断和未知。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
| --- | --- | --- | --- | --- |
| 架构与调用链 | 无法解释 | 只列技术栈 | 正常链路正确 | 跨层契约和状态归属清楚 |
| 模块实现 | 无法定位 | 只说用途 | 能讲关键过程 | 能指出源码、字段和边界 |
| 失败与安全 | 混淆／绕过 | 只说有审批 | 能讲一个失败 | 版本、取消、unknown 均清楚 |
| 取舍 | 无理由 | 泛泛优缺点 | 比较替代方案 | 结合本项目代价作判断 |
| 证据与贡献 | 虚构或归属错误 | 无实测 | 有本人记录 | 证据精确且限制清楚 |
| 表达 | 难以理解 | 堆名词 | 主干清晰 | 先主干、再证据，能应对追问 |

目标为 14/18，且不能出现证据或贡献归属错误。若不能解释一个主题，记录具体缺口，例如“审批过期如何检查”，回到相应模块和测试；不要只记“继续学权限”。

## 可用于简历的事实边界

| 掌握／参与情况 | 可以怎样写 |
| --- | --- |
| 只完成阅读 | “系统分析本机 Agent 的运行时、工具执行与恢复机制” |
| 本人做了隔离复现 | “基于隔离夹具复现补丁版本冲突／请求去重，并核对文件与事件断言” |
