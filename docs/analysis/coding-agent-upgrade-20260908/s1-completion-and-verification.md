## 1. 阶段目标与边界

让桌面主链能可靠区分“模型结束回答”“操作执行完毕”“用户要求已验证”。优先修复 G01/G02，并将验证失败反馈回同一 Agent 循环。本阶段不增加通用 shell 权限，不建设持续终端，不要求所有分析任务都执行工具。

完成验证约束的是产品声明和运行结果，不可能证明任意自然语言需求完全正确。无法自动判断的条件必须保留为待人工检查，不能伪装成机器验证通过。

## 4. 详细设计

### 4.1 结果分层

实现遵循 S0 冻结契约：ExecutionResult 的 `outcome` 为 `exited | timed_out | cancelled | failed | unknown`，正常非零退出仍是 `exited`；另用 `command_kind` 和 `validation_outcome=succeeded | failed | unknown` 解释命令业务结果。保留真实 `exit_code` 和输出引用，协议失败不能制造 exit_code=0。此决议替代草案把 succeeded 混入进程事实的方案。

命令类别决定退出码规则：pytest 的 1 代表测试失败；搜索工具的 1 可表示正常无匹配；普通开发命令默认 0 成功。规则由受审查的工具定义或项目验证配置确定，模型不能临时把失败码加入“允许成功”。对无法解释的命令保留原始结果并标未验证。

运行层保持 `status` 生命周期，并新增 `goal_outcome`：

| goal_outcome | 含义 | UI 文案方向 |
| --- | --- | --- |
| answered | 纯分析、解释或预览已完成，没有声明已执行修改 | 已回答/已生成预览 |
| verified | 全部必需条件已满足；机器检查有有效证据，必需人工确认有明确记录 | 已验证完成 |
| unmet | 已知必要条件不满足，纠偏结束 | 未完成，列出失败项 |
| blocked | 权限、环境或用户输入阻止继续 | 等待处理，显示具体原因 |
| unknown | 历史记录无验证或副作用结果不确定 | 未确认结果 |

工具拒绝不等于整段对话必然异常；Agent 可以准确报告阻塞。但用户拒绝后不得换工具完成同一被拒绝操作，S1 需要记录被拒绝操作的语义范围和参数关联。

### 4.2 最小任务完成要求

实现扩展 S0 的 `Requirement`，保持 `requirement_id`、`description`、`required`，增加 `kind`、`scope`、`origin`、`evidence_policy`；未另建重名契约。支持文件实际变化、指定命令执行、测试结果、产物存在、仅预览及不能自动确认的 manual 条件。manual 保留 unverified，本阶段未实现人工验收记录界面。

要求来源优先为用户显式约束和界面明确选项；模型可提出要求草稿，但不能自行取消用户要求。自然语言意图规则存在误判，必须提供可见的任务理解摘要；不明确时允许询问，不用关键词强制生成破坏性动作或虚构隐藏验收。

例如“解释这个函数”没有写入要求；“创建 hello.py”需要实际文件证据；“只给方案”不要求落盘；“修复并测试，但暂时不允许运行命令”应交付修改及“验证受阻”，不能宣布测试已通过。

### 4.3 证据模型

已实现 `EvidenceRef`：关联 `run_id`、`operation_id`、来源事件序号、内容摘要、验证时间及工作区版本；工具证据携带真实工具调用和 execution ID，纯回答/产物检查不伪造执行 ID。文件证据核对实际存在、写后摘要及当前状态；命令证据核对真实退出、是否超时/取消、验证目标及其输入代码版本。

测试通过后如果相关代码再次变化，旧测试证据失效或明确标记过期，不能被后续最终完成判断重复使用。先按保守的工作区变更版本处理，后续再优化依赖粒度。

文件写后摘要只证明写入一致，不证明功能正确；命令退出码 0 也不证明任意需求成立。结果报告应呈现证据的实际含义。

### 4.4 纠偏和结束

1. 模型准备给出最终回答时，运行验证器读取持久化事实。
2. 条件满足：提交结果和最终回答。
3. 条件不满足但可继续：将缺失/失败事实作为结构化反馈送回模型；沿用现有至多两次验证纠偏的能力，计入同一任务预算。
4. 权限拒绝或环境不可用：不自动改变权限、安装依赖或降级到云端执行。
5. 达到纠偏预算：结束并列出未满足条件；不能把最后一次语言回复当作成功。

验证器运行异常要失败关闭，并使用安全错误类别，不能吞掉异常后回退“通过”。

## 5. 数据与 API 变化

S1 优先在现有运行/执行 JSON 中增加带版本字段和结构化业务结果，避免只为少量字段立即重建表。若需要按证据查询的独立索引，按 S0 冻结的迁移机制加入，不预设当前数据库已升级。

结果以 `run_outcome` 携带 `goal_outcome`、`requirements`、`verification_results`、`evidence_ids`、`evidence_refs`、`unverified_items`；GET 运行快照和现有终态事件同步携带。创建运行接受可选 `completion_contract_version=1.0` 和用户要求，拒绝未知版本；SQLite 保持 3，仅扩展 JSON，不增加完成接口。

沿用共享核心已有 `output.validation_started`、`output.validation_passed`、`output.validation_failed`，没有新增一套平行验证事件。结果、最终消息和持久终态在现有事务中提交。

旧运行没有结果字段时映射 unknown。导入历史不补造证据，不更改已有审批和授权。旧服务端消费者保留兼容入口并通过回归。

## 7. 测试矩阵

| 用例 ID | 输入/故障 | 必须断言 |
| --- | --- | --- |
| S1-T01 | 明确要求写文件，模型零工具说完成 | 目标未验证，磁盘无变化，不能展示已修改成功 |
| S1-T02 | pytest 返回 1 | 命令验证失败，模型收到真实失败，最终状态不误报 |
| S1-T03 | 搜索无匹配返回 1 | 正常空结果，不泛化成执行器损坏 |
| S1-T04 | 写入工具伪报成功但磁盘无目标 | 文件证据无效，禁止 verified |
| S1-T05 | 仅生成 patch 预览 | 要求执行时不足；用户只要预览时可 answered |
| S1-T06 | 测试通过后再次修改代码 | 原测试证据过期，不自动沿用 |
| S1-T07 | 用户拒绝写入后模型换工具重试 | 同一拒绝范围不能被绕过 |
| S1-T08 | 用户只问解释 | 可零工具 answered，不误要求写文件 |
| S1-T09 | 命令超时/取消/宿主崩溃 | 原因分别保存，无伪造退出码 |
| S1-T10 | 验证失败两次以上/验证器异常 | 有界结束，公开未完成项，预算不重置 |
| S1-T11 | 最终消息写入失败 | 不提前发出已验证终态 |
| S1-T12 | 旧记录与重复终态事件 | 旧结果 unknown，投影幂等 |

单测先验证语义与事实加载器，再通过 `test_local_executor` 的 ASGI/SQLite 夹具覆盖完整创建、工具、验证、落盘、读取。UI 使用同一 payload 的契约夹具，不能另编一份总成功的预览数据。

执行命令沿用 S0 隔离启动器，加入新完成测试和本阶段 spec；共享核心变更还需跑既有 AgentRuntime/结果验证回归。阻塞和未执行项逐条记录。

## 8. 验收、兼容与回滚

- S1-T01 至 S1-T12 全部完成；确定性虚假完成负例必须正确拒绝。
- 运行失败、命令失败、目标未满足在 API 与 UI 中含义一致。
- 只分析和只预览任务不被错误阻塞；验证结果缺失时不补造通过。
- 旧服务端测试仍有效，不能删除其完成门禁以适配新核心。
- 若上线后出现误判，禁用新增自动完成声明、保留未验证结果与证据；不能以回滚为名恢复已知假成功语义。
- 完成判定修订不重放历史操作；回退程序先检查 schema 兼容，不用旧数据库覆盖新工作。
- 更新统一客户端和验证文档；共享项目状态记忆按明确授权处理。交付中列出剩余终端、上下文和恢复限制。
