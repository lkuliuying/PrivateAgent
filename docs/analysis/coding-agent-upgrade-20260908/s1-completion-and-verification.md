## 4. 详细设计

### 4.1 结果分层

实现遵循 S0 冻结契约：ExecutionResult 的 `outcome` 为 `exited | timed_out | cancelled | failed | unknown`，正常非零退出仍是 `exited`；另用 `command_kind` 和 `validation_outcome=succeeded | failed | unknown` 解释命令业务结果。保留真实 `exit_code` 和输出引用，协议失败不能制造 exit_code=0。此决议替代草案把 succeeded 混入进程事实的方案。

命令类别决定退出码规则：pytest 的 1 代表测试失败；搜索工具的 1 可表示正常无匹配；普通开发命令默认 0 成功。规则由受审查的工具定义或项目验证配置确定，模型不能临时把失败码加入“允许成功”。对无法解释的命令保留原始结果并标未验证。

运行层保持 `status` 生命周期，并新增 `goal_outcome`：

| goal_outcome | 含义 | UI 文案方向 |
| --- | --- | --- |
| answered | 纯分析、解释或预览已完成，没有声明已执行修改 | 已回答/已生成预览 |
| verified | 全部必需条件已满足；机器检查有有效证据，必需人工确认有明确记录 | 已验证完成 |
| unmet | 已知必要条件不满足，纠偏结束 | 未完成，列出失败项 |
| blocked | 权限、环境或用户输入阻止继续 | 等待处理，显示具体原因 |
| unknown | 历史记录无验证或副作用结果不确定 | 未确认结果 |

工具拒绝不等于整段对话必然异常；Agent 可以准确报告阻塞。但用户拒绝后不得换工具完成同一被拒绝操作，S1 需要记录被拒绝操作的语义范围和参数关联。

### 4.2 最小任务完成要求

实现扩展 S0 的 `Requirement`，保持 `requirement_id`、`description`、`required`，增加 `kind`、`scope`、`origin`、`evidence_policy`；未另建重名契约。支持文件实际变化、指定命令执行、测试结果、产物存在、仅预览及不能自动确认的 manual 条件。manual 保留 unverified，本阶段未实现人工验收记录界面。

要求来源优先为用户显式约束和界面明确选项；模型可提出要求草稿，但不能自行取消用户要求。自然语言意图规则存在误判，必须提供可见的任务理解摘要；不明确时允许询问，不用关键词强制生成破坏性动作或虚构隐藏验收。

例如“解释这个函数”没有写入要求；“创建 hello.py”需要实际文件证据；“只给方案”不要求落盘；“修复并测试，但暂时不允许运行命令”应交付修改及“验证受阻”，不能宣布测试已通过。

### 4.3 证据模型

已实现 `EvidenceRef`：关联 `run_id`、`operation_id`、来源事件序号、内容摘要、验证时间及工作区版本；工具证据携带真实工具调用和 execution ID，纯回答/产物检查不伪造执行 ID。文件证据核对实际存在、写后摘要及当前状态；命令证据核对真实退出、是否超时/取消、验证目标及其输入代码版本。

测试通过后如果相关代码再次变化，旧测试证据失效或明确标记过期，不能被后续最终完成判断重复使用。先按保守的工作区变更版本处理，后续再优化依赖粒度。

文件写后摘要只证明写入一致，不证明功能正确；命令退出码 0 也不证明任意需求成立。结果报告应呈现证据的实际含义。

### 4.4 纠偏和结束

1. 模型准备给出最终回答时，运行验证器读取持久化事实。
2. 条件满足：提交结果和最终回答。
3. 条件不满足但可继续：将缺失/失败事实作为结构化反馈送回模型；沿用现有至多两次验证纠偏的能力，计入同一任务预算。
4. 权限拒绝或环境不可用：不自动改变权限、安装依赖或降级到云端执行。
5. 达到纠偏预算：结束并列出未满足条件；不能把最后一次语言回复当作成功。

验证器运行异常要失败关闭，并使用安全错误类别，不能吞掉异常后回退“通过”。

## 9. 2026-09-16 完成要求提取修订

原实现只要全文出现写入动作，就把全文所有文件引用都视为必须修改的目标。原生任务“仅修改 sample.py，随后执行 python verify.py”因此误要求修改验证脚本。共享核心 `completion.py` 现按肯定写入动作的范围提取目标，读取、参考、执行及否定写入范围的文件不生成 `file_changed`；逗号和换行只继承纯文件列表。前置宾语、多文件清单、去重和最多 32 项的边界继续受测试约束。

没有明确文件名的肯定写入请求仍保留通用文件变化要求；用户显式 requirements、仅回答/预览策略、命令判定及文件证据检查保持原契约。提取结果只描述待验证目标，不新增文件写入权限，也不替代审批和项目授权。自然语言规则仍有覆盖范围，不能视为通用语义解析器。

普通 `python verify.py` 的退出码 0 只证明进程正常退出；未分类命令仍为 `validation_outcome=unknown`。已有运行生命周期可结束为 `completed` 并报告 `goal_outcome=unknown`，不得将其展示或记载为 `verified`。本次闭环使用既有 pytest 判定规则，保留普通脚本未确认、未修改目标文件及拒绝路径断言。

本轮复现、修复候选身份和原生验证结果集中记录在 [完成要求修复与原生闭环验证](s6-completion-requirements-native-validation.md)。此前 S6 候选及原生创建修复报告保持原文和历史时点；本次不重放历史操作，不重复 C 真实模型调用，不修改 `docs/project-state.md` 历史快照。

## 10. 2026-09-17 统一任务解释与执行限制

本节对应[三步改进的第一阶段](../agent-improvement-20260917/step-1-intent-and-constraints.md)。第 9 节的文件目标识别规则已迁入共享核心 `task_intent.py`，`completion.task_requirements` 保留兼容委托。内部 `TaskInterpretation` 保存 schema 1.0、目标版本、用户原文与 steer 来源、可组合动作、有效要求和 `TaskPolicy`；用户原文及显式要求用于重建，派生缓存只能收紧限制。项目指令继续通过既有来源和信任链进入上下文，不能扩大用户授权。

这些内部字段存入既有运行 JSON，`runtime.snapshot` 不暴露 `task_interpretation`。公共 `Requirement`、`RunOutcome`、事件结构和生成的前端协议不变；SQLite 维持当前 schema 7。创建、追加和恢复使用同一解释规则，沿用已有 generation、目标版本、审批失效和事务机制；关联恢复保留终止父任务原记录。

禁止测试、禁止命令、禁止写入、预览与路径范围分别表达。追加写入/访问范围取交集，禁止写入路径取并集。`task_constraints.py` 在模型工具过滤、文件读写、审批复核、实际宿主启动、stdin 以及 patch 最终落盘处检查；普通审批不能解除限制。无法证明遵守限定写入范围或禁止测试要求的脚本会被拒绝，包括表面名为 build/verify 的封装命令。这是对第 9 节“只提取目标、不提供操作授权”的执行侧补充；原来合法的目标提取结果不保证脚本能在更严格约束下放行。

被用户禁止的测试或命令不再成为必须补做的验收义务。冲突、未执行的验证和行为要求原句分别进入现有未验证结果；`manual` 不会因文件写入成功而通过。运行输出保留已核实操作并明确剩余条件，不沿用模型虚假成功措辞。后续禁止项不抹掉先前真实执行记录。纯解释与预览仍可 answered；行为条件未核验或明确禁止测试的修改任务不能仅凭写盘声明全部 verified。

## 11. 2026-09-18：区分辅助命令审计与验收义务

第一阶段候选版 1.0.7 的 T01 用户回执暴露：将全部命令尝试升级成必过要求，会让未启动的工具拒绝和修改前的正常诊断阻塞最终已满足的任务。修复记录见 [1.0.8 定向修复](../agent-improvement-20260917/phase-1-trial-1.0.8.md)。

- 原始、追加及显式要求继续按当前代码版本和证据校验，不因命令属于诊断而豁免。
- 自动补充要求时，尚未启动且没有执行/文件/补丁事实的 local_tool_rejected 只留审计；用户拒绝、权限及未知结果的原有控制继续生效。
- 按规范化命令聚合尝试。最新尝试有对应完成事件、正常退出、已知工作区摘要且确认没有工作区变化，并且不是已分类的测试时，可作为辅助观察保留在执行记录；不据此声称任何业务验证通过。同一命令先前产生或无法核对的副作用不能被后一次观察抹去。
- 测试、未恢复的失败、未知结果、实际文件写入继续产生验收义务。命令报错和证据过期消息带上对应命令，便于对照执行过程。
- 本次不修改公开契约、数据库版本、执行授权或用户约束；旧执行事件和结果原样保留。不会回写旧任务的终态，也不会自动重跑用户项目。
