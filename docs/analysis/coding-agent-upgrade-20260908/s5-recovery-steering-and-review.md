## 1. 任务目标与验收场景

将单次、内存中的执行扩展为可核对现场的持续任务。用户应能在执行中补充约束，在长任务期间暂停或取消，在应用重启后看到已完成的操作和不确定项，并在明确边界继续工作。

代表场景：Agent 修改两个文件、启动测试后应用意外退出。重启后展示文件修改事实，核对测试进程与输出，区分已结束、仍运行和结果不明；继续任务时保留原目标、用量和失败尝试，不重新盲写文件或重复启动未知状态的命令。

本阶段同时提供任务归属明确的 diff、同一工作区写入协调和不同工作区的有界并发。worktree 是用户可选择的隔离方式，不自动创建提交、合并或推送。

## 2. 当前能力与边界

- [共享运行时](../../../src/private_agent_core/runtime.py)已有检查点与 `resume`，主要处理等待审批的精确工具序列；它不是通用的桌面崩溃恢复入口。
- [本机运行时](../../../src/private_agent_local/runtime.py)通过内存任务、审批等待与账号级活动运行限制管理执行。需要补上持久化控制意图和恢复协调。
- [本机 Store](../../../src/private_agent_local/store.py)在启动恢复时将活动运行收束为失败。这是当前保守处理，不能简单删除后宣布任务可恢复。
- [运行投影](../../../apps/desktop/src/features/coding/model/runProjector.ts)、[运行流](../../../apps/desktop/src/features/coding/composables/useRunStream.ts)和 [diff 展示](../../../apps/desktop/src/features/coding/components/DiffArtifact.vue)可复用，但必须以新的后端事实投影为准。

## 4. 检查点与恢复协议

### 4.1 检查点内容

检查点保存恢复所需引用和事实，不复制所有大文本。拟议字段包括：

| 数据 | 内容与不变量 |
| --- | --- |
| 身份与归属 | 账号、project/session/run ID、逻辑任务 ID、工作区规范身份 |
| 版本 | 检查点格式、核心/宿主协议版本、模型能力与配置快照引用 |
| 上下文 | 已提交 ContextItem 游标、摘要检查点、当前目标与约束版本 |
| 执行位置 | 已确认模型响应、待执行工具序列、对应 operation ID 和参数摘要 |
| 运行事实 | 执行会话引用、补丁结果、完成证据、未知结果列表 |
| 预算 | 已消费用量、尝试次数、逻辑任务累计时间和剩余预算 |
| 授权关联 | 原审批记录与适用范围引用；恢复时必须重新检查有效性 |
| 一致性 | 运行状态版本、已提交事件序号、写入时间、内容摘要 |

授权关联用于审计，不是可重放的授权令牌。过期、已撤销、旧账号或作用对象变化的批准不能通过恢复重新生效。

### 4.2 必须落检查点的边界

1. 完整模型响应通过协议校验后、准备执行工具前。
2. 工具意图与审批等待建立时；批准后、执行前再次核对操作对象。
3. 补丁或命令结果持久化后、将结果反馈模型前。
4. steer 被接收和被应用时，两种事实分别记录。
5. 暂停到达安全边界、压缩提交、运行终结时。

状态、检查点引用和对应事件在同一 SQLite 事务提交。文件或进程副作用按 S3/S4 先记意图再核对结果，不宣称与数据库构成原子事务。检查点不能引用尚未成功落盘的内容块。

### 4.3 推荐恢复语义

活动进程内的暂停和继续保留同一个 `run_id`。异常退出后的旧运行保存为明确的中断记录；继续工作创建关联的新运行，使用拟议 `resumed_from_run_id` 和逻辑任务 ID 串联。旧事件和旧终态保持不可变，预算沿逻辑任务累计，不能借新 ID 自动清零。

拟议增加 `paused`、`interrupted` 等生命周期状态，准确枚举在实现前冻结。它们不取代 S1 的 `goal_outcome`。不支持新状态的客户端不得驱动恢复；旧记录缺少检查点时只允许基于现有历史发起新任务，不能声称精确续跑。

启动时先取得恢复协调锁并核对进程身份、内容摘要和操作日志，再将运行标为可继续或受阻。不能仅凭 PID 判断旧执行仍属于本任务；应结合宿主启动身份、会话 ID 和平台进程信息，防止 PID 复用。

| 崩溃位置或对象 | 恢复动作 |
| --- | --- |
| 尚未开始的只读工具 | 核对当前范围和预算后允许重新读取，记录这是新读取 |
| 完整模型响应尚未确认 | 记录未完成尝试；允许有界新请求，不拼接为原响应 |
| 文件当前摘要等于操作前摘要 | 可判定目标文件尚未呈现该写入；仍核对整个操作集和授权再决定执行 |
| 文件当前摘要等于操作后摘要 | 将已核实文件纳入恢复事实；结合操作日志确认归属，避免仅凭相同内容推断来源 |
| 文件既不等于前摘要也不等于后摘要 | 标冲突，保留文件，请求明确处理；不得回放或覆盖 |
| 命令存在可认证的活动执行会话 | 重新附着输出与状态，不再次启动 |
| 命令已记录退出和完整结果 | 复用证据；核对输入代码版本是否仍匹配 |
| 命令已开始但无法确认结果 | 标未知副作用，停止依赖它的自动执行；幂等键不足以证明安全重跑 |
| 等待审批、授权已失效 | 原等待关闭或失效，展示当前对象并重新按策略处理 |

对测试、构建、安装脚本也不能笼统视为无副作用。只有已验证为可安全重试的操作才能自动重试；外部网络和子脚本的“恰好一次”执行不在本机日志的保证范围内。

## 5. 运行中协作的行为设计

### 5.1 控制接口

沿现有 Run API 与私有传输新增控制能力。以下路径为提案，最终以统一 Schema 为准：

| 意图 | 拟议接口 | 核心参数与返回 |
| --- | --- | --- |
| 补充约束 | `POST /runs/{id}/steer` | `message_id`、预期状态版本、用户内容；返回接收 ID 和应用状态 |
| 暂停 | `POST /runs/{id}/pause` | 请求 ID、预期状态版本；返回暂停请求已接收或当前已暂停 |
| 继续 | `POST /runs/{id}/resume` | 请求 ID、检查点引用；返回原运行继续或关联新运行 ID |
| 取消 | 复用并扩展既有取消入口 | 保留兼容；区分已请求、进程已终止、清理失败 |
| 查询现场 | `GET /runs/{id}/recovery` | 可继续性、未知副作用、待核对对象、失效授权和限制 |

请求 ID 保证重复点击不会重复建立新运行或重复追加消息。版本冲突返回可解释的冲突结果及最新版本，前端不能静默覆盖新状态。

### 5.2 steer 生效规则

- 新指令先作为真实用户输入持久化，随后产生接收事件；前端显示“等待应用”，不能提前说“已按新要求执行”。
- 在模型请求前、工具调度前等安全边界消费输入队列，产生已应用事件并记录目标/约束版本。
- 如果正在等待模型响应，允许中断请求并记录被废弃尝试；迟到响应通过执行代次检查丢弃，不得执行其中工具。
- 如果正在执行写入或命令，追加约束不等于该操作已停止。涉及当前操作冲突时先进入停止或核对流程，说明已发生的副作用。
- “不要测试”“只解释”“停止写文件”等约束更新 S1 证据要求和 S2 上下文，但不能把已有失败记录改成通过。
- 用户改变总体目标时创建新的目标版本；重大独立任务按新任务处理，不能无限延长原任务且规避预算。

### 5.3 暂停、取消和继续

暂停表示不再派发新工具，并在可验证边界保存现场；它不代表任意 OS 进程可冻结。长命令默认按 S4 的取消协议收束，明确保留的开发服务单独列出。取消则终结本次运行并清理其应回收资源，用户后续继续通过关联新运行完成。

已有审批等待应持久化。暂停/取消/撤权之间的竞态由状态版本与单一调度器决定；任何迟到批准都必须重新检查当前状态。恢复时模型不可用、工具协议变化或剩余预算不足，展示阻塞原因，不悄悄切换模型或扩权。

## 6. 工作区协调与 worktree

### 6.1 并发模型

第一版使用“同一真实工作区最多一个可变更任务”的规则，不建设复杂文件锁图。会产生输出文件的测试和构建也按可变更任务处理；只有明确声明并验证为只读的工具才允许并行。

锁键以规范化工作区身份为准，处理同路径被重复登记、大小写差异和受支持的路径别名，不能仅依赖 project ID。内部锁不能阻止编辑器等外部写入，S3 的摘要检查仍必须存在。

不同工作区可并发，但受账号级模型、执行进程、输出空间和内存配额约束。初始并发上限在 S0/S4 测量后配置；队列位置、等待原因和取消均可见。为运行上下文、审批、模型用量和输出路由使用独立对象，禁止共享“当前运行”可变槽位。

租约带持有者和代次。进程失联不能仅因超时就强行认为外部副作用已结束；应先进入恢复核对，避免旧宿主和新运行同时写同仓库。

### 6.2 worktree 方式

用户可以选择当前目录或独立 worktree。创建前检查 Git 可用性、仓库类型、目标目录、磁盘空间、现有分支和工作区状态。起点明确为已选 ref；如果用户要求带入未提交修改，必须单独定义复制与冲突流程，第一版不自动承诺支持。

使用结构化 Git 参数创建 worktree，保存主仓库、worktree、ref 和所有权记录；正确处理 `.git` 文件与主仓库元数据关系。规则加载和读写范围基于实际工作树，不能把主仓库任意文件隐式纳入写权限。

结束后提供 diff 和保留/清理入口，不自动提交、合并或推送。清理必须核对目标是本应用创建的记录、路径归属明确且没有需保留的修改或任务；存在修改时保留并说明原因。禁止通过 `git reset --hard` 或 `git clean` 使清理条件成立。

## 7. 任务变更审查

以 S3 的实际操作日志和前后内容为主证据，结合当前 Git 状态构建三个可解释视图：本任务已记录的改动、任务开始前已有改动、无法归属或执行后出现的外部改动。归属不明时明确标注，不能全部算作 Agent 产出。

diff 支持文件新增、修改、删除、移动、二进制摘要和大文件截断提示。对命令或脚本造成的更改，通过执行前后范围快照归集候选变化，但标明同时有外部写入时不能精确归因；忽略目录的变化不应伪装为完整仓库审计。

用户从审查界面发起的撤销复用 S3 操作服务：当前内容必须仍等于待撤销操作的后摘要；冲突时保留用户后续修改。多操作撤销必须检查顺序和依赖，撤销本身生成新操作记录。UI 不直接调用任意 Git 回退命令。

新增测试应分别覆盖纯状态机、真实 SQLite、真实临时仓库、真实 exec-host，以及 Tauri→本机服务→UI 链。模拟函数返回值不能替代崩溃后的文件和进程现场检查。每个故障点使用独立测试目录，保留可核对的脱敏证据。

## 10. 退出条件、回退与交接

- S5-T01–S5-T15 全部通过；总体路线的“零自动重复未知副作用”“零静默覆盖”和取消门禁满足。
- 用户可完成“开始修改→追加约束→暂停→继续→重启→核对现场→继续验证→审查 diff”的实际桌面流程。
- 同工作区锁与跨工作区配额通过并发测试；worktree 的创建与清理范围可审计。
- 新旧记录、检查点版本、宿主身份和预算归属均有兼容证据；未知状态始终可见。
- 文档记录支持恢复的边界和不支持的命令副作用，不宣称任意任务都能从任意指令位置精确恢复。

回退时先停止新任务和恢复调度，收束可控宿主，保留检查点、操作日志和未决状态。可以关闭新并发、steer 或 worktree 功能，但不能清空未知操作后假装无事发生，也不能回到覆盖用户改动的撤销方式。
