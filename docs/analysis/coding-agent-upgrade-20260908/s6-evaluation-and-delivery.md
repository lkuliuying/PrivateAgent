## 1. 任务目标

证明用户从实际安装的桌面客户端进入项目后，可以完成开发任务；同时证明失败、权限不足、重启和版本升级时，系统不会伪报成功、静默丢失工作或扩大授权。

验收分成独立结论：源码检查、确定性测试、真实宿主集成、真实模型质量、安装升级、生产发布。前一类通过不自动推出后一类通过。当前阶段可以形成交付决议，不自行执行生产发布、账号操作或付费调用。

## 3. 任务集合与实验设计

### 3.1 基础任务集

首轮使用 3 类小到中等规模的可分发样例仓库：Python 后端、Vue/TypeScript 前端、Rust 工具或服务。每类 10 题，共 30 题。任务来源、许可证、初始 revision、依赖和标准验证命令必须固定，不使用生产代码、私人账号数据或真实密钥。

| 任务类别 | Python | Vue/TypeScript | Rust | 合计 | 主要检查 |
| --- | --- | --- | --- | --- | --- |
| 修复可复现缺陷 | 2 | 2 | 1 | 5 | 定位、边界条件、回归测试 |
| 实现小型跨文件需求 | 2 | 2 | 1 | 5 | 调用链、契约一致、测试与文档 |
| 有行为约束的重构 | 2 | 1 | 2 | 5 | 多文件补丁、不改变既有行为 |
| 大文件或长上下文任务 | 1 | 2 | 2 | 5 | 搜索续读、规则、压缩后约束保留 |
| 执行失败与中断接续 | 2 | 1 | 2 | 5 | 测试失败修复、重启继续、未知副作用 |
| 用户工作与权限边界 | 1 | 2 | 2 | 5 | dirty 仓库、并发编辑、拒绝授权后的正确处理 |
| 合计 | 10 | 10 | 10 | 30 | 每题只有一个主分类，避免重复计算 |

每类仓库 6 题用于开发回归、4 题作为保留集，即开发集 18、保留集 12。S0 冻结第一版，S6 开始前核对代表性和环境前提。保留集的标准答案与隐含测试不放入 Agent 可读取的项目工作区；运行器在隔离验收端执行隐藏断言。

“拒绝授权后正确停止”是系统边界测试成功，但不能记为“代码需求独立实现成功”。每题清单分别定义 `expected_system_behavior` 与 `coding_goal` 是否应完成，质量指标只统计预先定义的可完成编码目标；同时报告全部 30 题的系统行为结果，不能把停止类题目用来抬高编码成功率。

### 3.2 重复次数与控制变量

每个选定模型执行 30 题各 3 次，共 90 次。各次使用独立、相同初始状态的工作区；不复用前次解答或缓存的工具证据。固定模型标识、Provider、上下文容量、能力开关、温度等可控制参数和单题预算；未提供可固定参数时如实记录。

先验收一个准备推荐的默认模型。其他模型按同一口径分别测试，不把强模型成绩用于弱模型，也不跨模型合并成功率来判定默认模型通过。远程模型可能更新，报告记录实际调用日期和可获得的模型版本信息。

本机模型先完成离线/回环测试。真实远程调用须在已有明确授权范围内确认模型、次数、单题预算与总预算上限；凭据沿现有安全配置读取，不写入任务清单、日志或报告。若未获真实调用授权，保留“质量验收未执行”，不能以假模型结果代替。

### 3.3 判定口径

一次可完成编码任务的“独立完成”必须同时满足：

1. 隐藏功能断言、必要回归和预先指定的验证通过。
2. 修改范围符合题目，初始用户修改和明确禁止项得到保留。
3. 没有人工指出实现位置、修补代码或追加解题步骤；允许任务原本要求的审批与需求澄清。
4. 最终报告与实际文件和测试事实相符，不把未执行检查报告为通过。
5. 在预设预算内结束，任务事件、结果和工作区可核对。

编码独立完成率 = 独立完成次数 / 清单中预先标记为可完成编码目标的全部启动次数。分母同时列出题数和重复次数；若 30 题均设计为有可完成编码目标，分母为 90。边界题若故意设置不可完成目标，须在启动前声明并单列，不能临时排除失败。

环境预检失败可阻止实验启动，但要在报告列出题目和原因；已经开始后出现 Provider 超时、工具失败、预算耗尽或误用命令，均按既定分类记录，不能从质量分母删除。故意注入不可恢复故障的专项测试单独报告恢复正确性，不混入普通质量实验。

至少报告每模型总体结果、每类任务结果、开发集/保留集结果、人工介入次数和失败分类。样本量有限，不据此承诺任意商业项目都有同样成功率。

## 4. 评测运行器与证据结构

已扩展 [统一客户端验证脚本](../../../scripts/verify-unified-client.py) 的 `--s6`，新增 `scripts/run_coding_acceptance.py` 和 `tests/coding_acceptance/s6_fixtures.py`。正式 IPC、独立目录和打包校验的实现边界见评测协议；下面的原始验收要求仍用于识别未完成项。

运行器必须做到：

- 每次创建已核对路径的新目录，加载样例与独立账号测试数据；不读取仓库 `.env` 或生产数据库。
- 设置明确的依赖与环境预检，缺少依赖时失败并说明，不自动联网安装或修改全局环境。
- 通过正式 API/IPC 驱动主链，不能绕过审批、完成验证器或把最终答案直接注入 UI。
- 记录失败、超时和取消，始终输出本次结果；运行器自身失败应使汇总门禁失败。
- 为子进程、回环服务和临时文件设置生命周期和配额；清理仅针对本次拥有且路径已核对的资源。
- 所有结果关联执行产物摘要；脱敏后保留必要输出，不保存授权令牌、完整环境或供应商请求头。

每次实验输出建议包含：

| 文件或记录 | 内容 |
| --- | --- |
| `manifest.json` | 清单版本、样例 revision、运行器版本、产物摘要、模型能力与预算 |
| `attempts.jsonl` | 每题每次状态、业务结果、失败分类、时间、用量、人工介入 |
| `events/` | 有序事件和游标；正文按引用存储并脱敏 |
| `artifacts/` | 任务 diff、文件摘要、命令结果和验证输入版本 |
| `metrics.json` | 分组指标、分母、缺失数据、门禁判定 |
| `report.md` | 可读结论、失败样例、限制、复现步骤与下一步 |

上述产物由每次 S6 实验在独立目录创建。版本库只放可分发 fixture、脱敏报告和必要的小型契约样例，不提交原始庞大日志。

以下是后续验收命令或入口设计，不表示本轮执行过。先按 [S0 测试隔离方案](./s0-baseline-and-contracts.md)准备独立环境，再从受影响的直接测试扩大到整链。

| 层次 | 使用方式 | 不能替代的验证 |
| --- | --- | --- |
| Python 核心与本机服务 | 既有 `.venv`、隔离启动器、相关 pytest 模块 | 真实进程和 UI |
| Vue 状态与组件 | 在 `apps/desktop` 执行 `npm run test -- <相关 spec 路径>` | Tauri 私有传输、安装程序 |
| TypeScript 与前端构建 | 在 `apps/desktop` 执行 `npm run build` | 真实模型质量和安装升级 |
| Rust 宿主 | 仓库根执行 `cargo test --manifest-path apps/exec-host/Cargo.toml` | 跨进程协议和实际 OS 隔离 |
| 浏览器端流程 | 在 `apps/desktop` 执行 `npm run e2e`，区分 fixture 与真实后端场景 | 原生桌面窗口和 Tauri IPC |
| 打包本机服务 | `scripts/verify-unified-client.py` 的 `--bundle`、`--work-dir`、`--model-mode` | 完整桌面 UI、真实账号或供应商 |
| 新评测运行器 | 完成后固定 CLI、样例清单和模式参数，再写入测试指南 | 任何未实际执行的测试 |

`verify-unified-client.py` 当前支持 `service`、`ollama`、`openai` 三种 `--model-mode`，均可使用回环替身验证契约。后续应补齐 S1–S5 的新事件、流式响应与恢复场景，不能只沿用旧脚本的成功断言。

[旧本机执行器 smoke 脚本](../../../scripts/verify-local-executor.py)以端口启动测试，是特定启动方式的检查。当前默认私有管道必须走相应真实链路，不能拿 TCP smoke 通过作为私有 IPC 通过的证据。

打包入口、签名方式和输出目录在验收时以仓库脚本为准，先阅读参数再执行。新增 Windows 桌面自动化工具或依赖需要单独核对适配与必要性；第一轮可以使用可复现的人工桌面步骤配合自动化后端证据，但必须标明人工执行范围。

## 6. 阻断门禁与度量

| 门禁 | 拟议标准 | 测量方式 |
| --- | --- | --- |
| S6-T01 完成真实性 | 固定假完成负例全部被正确识别 | 文本、业务结果、文件和测试证据交叉检查 |
| S6-T02 写入保护 | 固定 dirty/并发修改用例无静默覆盖 | 前后摘要、补丁日志、实际 diff |
| S6-T03 副作用恢复 | 故障矩阵无自动重复未知副作用 | 检查点、operation ID、实际文件/进程 |
| S6-T04 事件一致性 | 无静默丢事件或重复终态 | 延迟、断线、重复帧、快照恢复 |
| S6-T05 取消与清理 | 可控进程树 5 秒内退出；异常明确阻塞后续冲突执行 | 平台进程观测与 UI 状态 |
| S6-T06 终端能力 | 10 分钟命令、持续服务、stdin、Unicode、大输出通过 | 真实宿主测试 |
| S6-T07 交互延迟 | 宿主输出收到后至 UI 可见 p95 ≤ 1 秒 | 同机可比较时钟与采样，注明负载和样本量 |
| S6-T08 权限边界 | 宣称支持的边界正反对照全部通过 | 文件、网络、子进程、撤权与降级行为 |
| S6-T09 编码质量 | 默认模型预先定义分母上的独立完成率初始目标 ≥ 80% | 每题每次证据，失败与人工介入保留 |
| S6-T10 协议兼容 | 支持矩阵内的新旧能力协商正确，不支持组合明确受阻 | 前端/本机核心/宿主/代理组合 |
| S6-T11 安装升级 | 支持环境的干净安装和旧记录迁移通过 | 实际安装产物与独立数据副本 |
| S6-T12 文档一致性 | 能力、限制、命令和部署结论均与证据一致 | 文档检查及独立复现 |

额外报告总耗时、模型等待、工具等待、审批等待、token、重试、压缩次数、峰值进程/存储使用。用量缺失标未知，不按零计费；跨 Provider 的成本估算记录计价日期和依据。性能使用固定机器、负载和样本量，不能只挑最快一次。

安全和数据保护门禁不能用质量成功率抵消。80% 编码成功率也不能抵消一次静默覆盖或授权越界。性能目标若需校准，应在实验前记录原因和新阈值，不能看到不达标后直接改报告。

## 7. 安装、升级和回退验收

### 7.1 环境矩阵

先在 S0 冻结产品实际支持的 Windows 版本与架构，再逐项验收；候选包括 Windows 10/11 x64，不由本计划自动扩大支持承诺。至少覆盖：

1. 没有源码目录和开发机 `.venv` 的干净环境，验证随包运行时能够启动。
2. 项目路径包含空格、中文，标准用户权限，指定项目可写而其他目录受限制。
3. 模型服务可用、不可用、鉴权失效、能力不足等情形，错误分类清晰。
4. Rust 沙箱或 PTY 不可用时的真实降级说明，与 S4 能力握手一致。
5. 应用正常退出、强制结束、系统重启后的宿主与数据恢复。

开发机 PATH、已安装 Python、Node、Git 等不能被偷偷当作随包能力。外部开发工具本就需要用户安装时，诊断面板明确列出缺项和项目命令要求，不在安装阶段擅自修改环境。

### 7.2 数据与协议升级

以当前 schema 3 数据结构为基线构造脱敏 fixture，并核对更早受支持版本的迁移入口。至少包含空库、旧完成记录、失败记录、审批记录、长输出引用、多账号隔离和未完成运行。较老版本未确认支持时明确列“待验证”，不许假设所有历史版本可直接升级。

迁移前使用一致性备份，迁移后校验记录数、关联完整性和内容引用。新字段缺失的旧记录沿 S1 显示未记录验证，不能升级成 verified。重启期间的旧活动记录遵守 S5 保守核对，不能借迁移自动重放操作。

协议组合至少检查：新 UI/新本机/新宿主、旧 UI 遇到新必需能力、新 UI 遇到旧运行时、模型代理未支持流式。能力协商应在开始任务前选定可用路径或明确受阻；运行中不可把中断的流式请求静默重发成完整请求。

### 7.3 回退边界

程序回退与数据回退分开验证。可关闭新功能时优先保留数据；旧程序不能读新格式时，应阻止直接降级启动，并提供已验证的数据导出或兼容路径。

从升级前备份恢复会遗漏升级后的任务和修改记录，不能当作无损撤销。只有在独立副本演练并明确新增数据保留方案后，才能编写正式操作步骤；生产执行仍需对应授权。

## 9. 决策、退出与后续范围

M3 的完成条件是：S6-T01–S6-T12 在声明范围内通过，默认模型质量达标，失败归因与限制可查，安装/升级/回退证据齐全，使用与运维文档与产物一致。任一阻断项未通过，应列出所属阶段、最小修复任务和需要重跑的验收，不能用“总体基本可用”替代结论。

最终交付决议应明确：

- 本次支持的 Windows、模型、Provider、工具和权限组合。
- 已通过、失败、未执行、不适用的检查及各自理由。
- 可用于日常开发的范围，仍需人工介入的常见失败类型。
- 是否满足受控试用或正式发布条件；发布行为本身是否已经获得授权和执行。
- 未解决问题的影响、负责人角色与下一步，不编造实际人员或承诺日期。

S6 后可以另立扩展任务评估 Skills、MCP、浏览器辅助与子 Agent。每项先给出所需用户场景、工具/数据权限、隔离和资源预算、验证方法，确认不会破坏本计划已建立的单一状态与授权来源，再制定独立开发计划。它们不作为本轮基础 Coding Agent 可用性的替代证据。
