# AI Agent 项目生态、生产生活与大众需求调研报告

**调研日期：2026-10-22（Asia/Shanghai）｜研究形式：公开网络与GitHub资料核验｜样本：54个仓库、13类生态、30个大众场景、12类生产需求**

## 核心发现

本报告研究的是以大语言模型为核心、能够调用工具并推进任务的软件 Agent，以及为其提供能力的开源生态。它同时回答“GitHub 上有什么”“数量应怎样计算”“企业和普通人需要什么”“哪些需求值得产品化”。

1. **GitHub 的供给已经形成多层生态。** 本次按 13 类整理并核验 54 个公开仓库，既有完整助手，也有开发框架、工作流平台、记忆层、沙箱和评测工具。54 是本报告样本量，不是行业项目总量。
2. **不能给出一个可信的全站 Agent 精确总数。** 2026-10-22 访问的 `ai-agents` 主题页显示 123,636 个公开仓库，但其中包含工具、教程及其他边界项目；不同标签还会重复。不能把主题数当成经过筛选的 Agent 产品数。[GitHub 主题页](https://github.com/topics/ai-agents)
3. **当前热点不再只围绕编程与框架。** 本次样本还出现常驻个人助手、跨渠道入口、团队 Agent 管理，以及从研究工具扩展为通用执行环境的产品。这个观察来自所选项目的当前说明，不是对全站趋势增速的测量。
4. **企业的需求更接近可核验的业务结果。** 客服工单、研发、内部知识和业务流程是重要落点；接入系统、处理例外、控制成本与人工复核，决定能否从演示进入常态使用。
5. **大众需求广泛，但并不都需要自主执行。** 信息查找、写作、学习、创作、购物决策和家庭事务具有不同的使用频率、数据门槛和风险。大众使用 AI 的证据，比大众愿意长期授权 Agent 的证据更充分。
6. **帮助做决定和代替行动之间存在显著差别。** YouGov 的美国调查中，65% 对 AI 比价持信任/接受态度，只有 14% 对代为下单持相同态度。这支持先提供决策材料、再由用户确认关键动作的产品形态，不能据此预测中国市场转化率。[原始调查](https://yougov.com/en-us/articles/53808-american-trust-in-ai-for-retail-consumer-sentiment-in-2025)
7. **机会应围绕持续发生的具体事务寻找。** 能保留状态、拿到输入、减少返工、证明节省了时间的窄流程，比单纯增加聊天入口、Agent 数量或工具数量更值得验证。此项是本报告的分析判断。

调研时间为 **2026-10-22，Asia/Shanghai**。项目热度与维护状态是当日访问快照；需求研究的调查时间分别列明，不把 2025 年研究改称 2026 年实测。

## 1. 范围、定义与研究方法

### 1.1 本报告怎样识别 Agent

采用操作性定义：系统接受目标后，能够根据中间结果选择下一步，调用外部工具或操作环境，并在一定范围内保存执行状态。可有人审批，不要求完全无人值守。

需要区分以下四种东西：

| 形态 | 主要行为 | 合适的任务例子 |
| --- | --- | --- |
| 聊天或内容生成 | 接收输入，提供回答、草稿或建议 | 翻译一段文字、解释概念 |
| 固定工作流 / RPA | 按已定义步骤与规则执行 | 固定格式报表、确定条件提醒 |
| Agent 应用 | 根据结果调整工具、步骤与处理分支 | 多来源核验、缺资料追问、执行后检查 |
| Agent 基础设施 | 为上层系统提供记忆、工具、运行和观测 | MCP 服务器、沙箱、追踪及评测 |

边界并不绝对：n8n、Dify 一类平台既能实现固定流程，也能承载 Agent；知识库产品也不一定在每次请求中执行自主循环。**本报告统计“相关生态”，不把所有项目都宣称为独立自主 Agent。**

不纳入主要比较的对象：传统监控 agent、单纯游戏 NPC、没有软件执行链的纯模型权重、实体机器人硬件。科研及行业 Agent 仅讨论软件侧；真实物理执行不与浏览器任务混为一谈。

### 1.2 证据如何分层

- **A：可直接核验的事实。** GitHub 公开 API 元数据、项目 README、调查机构原始表格、研究摘要。
- **B：受样本或发布方影响的证据。** 企业自报调查、厂商调查、项目功能与效果的自我描述。必须保留对象和分母。
- **C：分析推断。** 对产品机会、需求频率、用户愿意承担的操作方式的判断。
- **H：待验证需求假设。** 场景目录中的具体产品闭环，尚未通过本次用户访谈、留存数据或付费试验验证。

A/B 并非简单的可信或不可信等级。例如公开 API 可以准确证明仓库的 Star 数，却不能证明真实用户量；随机实验可以支持特定助手的效果，却不能证明另一款 Agent 有相同效果。

### 1.3 本次实际做了什么

1. 访问 6 个 GitHub 相关主题页，记录其公开仓库计数及统计边界。
2. 综合主题页、公开检索与典型工具链，目的性选择 54 个仓库；逐个读取公开仓库元数据，以稳定的 repository id 去重。
3. 对迁移、归档、许可和定位容易变化的 16 个项目补读 README；其余项目以元数据和简述核验，不宣称完成源码审计。
4. 查阅 CNNIC、Pew、YouGov、McKinsey、Docker 及 NBER 原始发布或可检索摘要；分别整理中国用户基础、美国消费者行为、企业采用和工具使用效果。
5. 以已有家庭管理和个人工具作为对照，区分“已有工具能解决的问题”和“需要 Agent 补足的流程”。

没有安装或运行这 54 个项目，没有测试其真实任务成功率、成本、中文体验或安全性；没有联系项目作者、购买付费报告、开展用户访谈或计算市场收入规模。本次是公开资料研究和项目快照，不是产品实测排行榜。

**对“总和”的回答：可以确认生态规模很大，但本次不能提供经过定义、清洗和去重的全站精确总数。** 这不是用样本数代替总体，而是保留无法从现有证据回答的部分。

主要原因：

- 搜索 `agent` 会包含监控、代理程序等非 AI 项目；只搜 `ai-agents` 又会漏掉未打标签的产品。
- 同一项目可以有 Python / JS SDK、文档仓库、示例、部署版和多个 fork；一个仓库也可能同时覆盖多个应用。
- 教程、论文实现、清单和生产应用混在同一个主题中。例如 `llm-agent` 页面里也出现语音生成项目，说明标签不能充当严格分类。
- Star 是累计关注，不是活跃使用或付费意愿；多个仓库的 Star 相加还会重复计算同一关注者。
- GitHub Search 存在结果窗口和分页限制；本次连接器搜索结果没有返回可用的全站 `total_count`，公共 Search API 网页读取也未成功。没有进行全量枚举。

如果后续确实需要正式项目普查，应先定义“仓库数、独立产品数或组织数”，再按标签和关键词分片取数、按 repository id 去重、标注 fork/归档/教程，并审查未命中与误命中样本。即便如此，公开仓库普查也不等于全部商业 Agent 的数量。

### 本报告的样本总览

- 核验仓库：**54 个**，repository id 去重后仍为 54。
- 分析类别：**13 类**，每个仓库只指定一个主要类别，用于阅读和样本计数。
- GitHub `archived=true`：**6 个**。
- 另有 **AutoGen** 的 README 明确声明停止维护并建议迁移，但本次 API `archived=false`。这是两种来源状态的差异，报告保留两者，不强行合并为同一个归档计数。
- 样本是有目的的覆盖选择，不可据此估计各类项目的 GitHub 市场占比。

完整字段见同目录 `github-repositories.json`；数量与外部证据见 `research-evidence.json`。

## 3. 13 类项目地图

分类依据是主要提供的价值和使用对象；一个项目可以有多种能力。下面的数量只描述本次 54 个样本的构成。

| 类别 | 样本数 | 主要使用者 | 实际解决的任务 | 选型时应注意 |
| --- | ---: | --- | --- | --- |
| 框架与多Agent编排 | 10 | 开发团队 | 组织模型、工具、状态和多角色协作 | 框架存在不等于业务应用已经可用 |
| 低代码与业务工作流 | 4 | 运营、企业IT、自动化团队 | 连接业务系统，组合流程与人工节点 | 需要区分规则流程与动态Agent |
| 编程与软件工程 | 5 | 开发者、研发团队 | 理解仓库，修改代码，运行验证 | 质量受项目背景、工具权限和验证影响 |
| 个人通用与常驻助手 | 6 | 个人用户、自托管用户 | 在常用入口持续处理多种个人任务 | 安装、授权与长期维护仍有门槛 |
| 浏览器与电脑操作 | 4 | 运营、行政、遗留系统使用者 | 在缺少稳定API时完成界面操作 | 登录、页面变化与动作验证是难点 |
| 研究与信息搜集 | 3 | 研究、产品、咨询及内容人员 | 检索、核验、综合并形成交付物 | 引用正确与覆盖完整需要单独验证 |
| 知识库与文档 | 3 | 企业员工、资料密集型个人 | 解析资料，检索证据，组织知识 | 纯RAG问答不必然是自主Agent |
| 数据与商业分析 | 2 | 分析师、业务人员 | 查询数据、解释结果、制作分析 | 权限、指标定义和错误查询是核心边界 |
| 语音与实时交互 | 2 | 客服、服务运营、语音产品开发者 | 通过实时语音交互并接入工具 | 实时体验不等于后续事务完成 |
| 记忆工具运行与观测 | 8 | Agent应用开发团队 | 接工具、保状态、隔离运行、追踪与评测 | 属于配套能力，不是终端业务结果 |
| 垂直金融与科研 | 3 | 领域研究者、专业组织 | 在专门知识与工具下协助领域任务 | 研究演示不能替代专业验收 |
| 基准评测与教程 | 3 | 研究者、开发者、学习者 | 检验能力、提供样例与项目索引 | 不能当作已部署的终端产品 |
| 团队Agent管理 | 1 | 团队负责人、AI平台人员 | 分派任务，设置权限和预算，复核结果 | Agent数量增加也带来管理和审阅成本 |

从开发依赖关系看，可以将它们理解为四层：**工具与运行基础 → Agent 开发与编排 → 任务型应用 → 多任务或团队管理**。这些层次之间存在复用关系，不是相互替代的竞争者。

例如，个人助手可以接入 MCP 工具、使用记忆组件，再通过浏览器执行操作；企业工作流平台可以在固定节点中调用 Agent；团队管理软件则在更上层管理不同执行器。只比较项目 Star，容易把基础设施、框架和成品混到同一张排名表里。

## 4. 当前项目格局与容易过时的结论

### 4.1 框架层：选择已有状态和运行能力，不必从零造编排

样本包括 [LangGraph](https://github.com/langchain-ai/langgraph)、[CrewAI](https://github.com/crewAIInc/crewAI)、[AG2](https://github.com/ag2ai/ag2)、[AgentScope](https://github.com/agentscope-ai/agentscope)、[Google ADK](https://github.com/google/adk-python)、[OpenAI Agents SDK](https://github.com/openai/openai-agents-python)、[Pydantic AI](https://github.com/pydantic/pydantic-ai) 和 [smolagents](https://github.com/huggingface/smolagents)。

它们为开发者提供不同的组织和运行方式，但不能替开发者决定真实业务中的对象、权限、异常和验收标准。“支持多 Agent”不自动意味着比单 Agent 或固定流程更好。应先用同一批任务比较成功率、人工复核和总成本。

**本次发现的维护变化：** [AutoGen README](https://github.com/microsoft/autogen) 已声明停止维护并引导新用户使用 [Microsoft Agent Framework](https://github.com/microsoft/agent-framework)。旧文章把 AutoGen 当成默认新项目首选时，需要重新核对。AG2 与 Microsoft 的后续框架应按各自仓库理解，不能因历史名称相近就视为同一产品。

### 4.2 低代码层：连接业务系统通常比“会聊天”更有价值

[Dify](https://github.com/langgenius/dify)、[n8n](https://github.com/n8n-io/n8n) 和 [Activepieces](https://github.com/activepieces/activepieces) 说明，流程画布、系统连接、模型能力与人工节点可以在同一平台组合。

适合的任务是“收到材料 → 提取信息 → 查询系统 → 生成待确认结果 → 写回或交接”。当流程分支是确定的，应优先使用规则节点；只有需要判断不确定输入或自主选择下一步的部分，才需要 Agent。

[Flowise](https://github.com/FlowiseAI/Flowise) 在本次 API 和 README 中均显示已归档，仍可作为历史设计参考，但不能按旧热度直接假定持续维护。

许可也是交付边界：n8n README 指向 Sustainable Use License 与 Enterprise License；Dify README 说明其许可基于 Apache 2.0 并附加条件。公开可读源码不等于任意转售、托管和商标使用都自动获准，实际商业使用应检查对应版本的许可文件。

### 4.3 编程层：任务结果较容易验证，产品比较也更具体

[OpenHands](https://github.com/OpenHands/OpenHands)、[Aider](https://github.com/Aider-AI/aider)、[Cline](https://github.com/cline/cline) 和 [Goose](https://github.com/aaif-goose/goose) 代表不同入口。它们面向代码、文件和开发工具，通常可以用差异、测试与运行结果检查交付。

本次确认 `block/goose` 已迁移至 `aaif-goose/goose`；[Roo-Code](https://github.com/RooCodeInc/Roo-Code) 的 API 显示已归档。维护状态、接入方式和当前版本比单张历史推荐清单更重要。

对新产品而言，只有聊天、文件编辑与终端调用时，较难证明独立使用价值。较具体的机会来自明确工作类型的验收、受限环境接入和可恢复的长任务；这些机会仍需要实际用户证据，不能从功能差异直接推导市场成立。

### 4.4 个人助手层：长期状态和现有入口成为重要设计对象

[OpenClaw](https://github.com/openclaw/openclaw)、[Hermes Agent](https://github.com/NousResearch/hermes-agent)、[nanobot](https://github.com/HKUDS/nanobot)、[ZeroClaw](https://github.com/zeroclaw-labs/zeroclaw) 和 [QwenPaw](https://github.com/agentscope-ai/QwenPaw) 均进入本次样本。

README 中可观察到的共同设计包括：连接日常通信入口、工具扩展、记忆或技能、持续运行与自托管。QwenPaw 的旧入口 `CoPaw` 已发生更名迁移。Hermes 对持续学习的描述属于项目方声明，本报告没有证明其长期学习效果优于其他产品。

这些项目说明个人助手形态具有开发者关注，但 Star 不能回答普通用户能否顺利安装、是否愿意接入真实账户、多久使用一次、是否愿意付费。将自托管开发者需求外推为全民需求，会忽略部署、模型配置和故障维护的成本。

### 4.5 浏览器与电脑操作：覆盖广，可靠执行的门槛也高

[browser-use](https://github.com/browser-use/browser-use)、[Skyvern](https://github.com/Skyvern-AI/skyvern)、[UI-TARS Desktop](https://github.com/bytedance/UI-TARS-desktop) 和 [OpenAdapt](https://github.com/OpenAdaptAI/OpenAdapt) 覆盖不同操作方式。

用户真正需要的是提交成功、资料正确、没有重复操作，并在失败时能接手。能点击页面只是其中一环。对于已有稳定业务 API 的任务，应比较 API 接入与界面操作的维护代价，而不因为 Agent 能看屏幕就默认使用屏幕操作。

OpenAdapt 当前项目简述强调从演示形成可重复程序，也提醒我们：一个产品可以把 AI 用在理解和生成流程的阶段，再由更确定的程序执行。任务完成并不要求每一步都交给模型判断。

### 4.6 研究与知识工具：研究过程和结论证据不能分开

[GPT Researcher](https://github.com/assafelovic/gpt-researcher)、[DeerFlow](https://github.com/bytedance/deer-flow) 是代表样本；[open_deep_research](https://github.com/langchain-ai/open_deep_research) 的 API 显示已归档。

DeerFlow README 明确说明 2.0 是重写，并扩展为使用子任务、记忆、沙箱与技能的通用执行环境。因此，将其继续只描述为旧版研究流水线，已经不准确。

知识侧的 [AnythingLLM](https://github.com/Mintplex-Labs/anything-llm)、[RAGFlow](https://github.com/infiniflow/ragflow) 和 [Onyx](https://github.com/onyx-dot-app/onyx)，与研究 Agent 有协同关系，但“找到一段文本”和“完成可核验研究”是不同验收目标。来源遗漏、错误引用和过期材料，都需要单独检查。

### 4.7 基础设施与团队管理：管理动作本身也是需求

[mem0](https://github.com/mem0ai/mem0)、[Letta](https://github.com/letta-ai/letta)、[MCP servers](https://github.com/modelcontextprotocol/servers)、[E2B](https://github.com/e2b-dev/E2B)、[Langfuse](https://github.com/langfuse/langfuse)、[Promptfoo](https://github.com/promptfoo/promptfoo) 分别覆盖记忆、工具、运行和评测等部分。

[Paperclip](https://github.com/paperclipai/paperclip) 的 README 则把目标、任务、预算、权限与审批放到团队管理层。这是一个独立产品方向：当团队已经有多个执行器时，需要看清谁在做什么、花了多少、结果如何。但本次只确认产品提供此类设计，没有核验其企业客户量或效果。

两个迁移信号值得保留：Daytona 的旧公开仓库 README 声明 2026 年 6 月后核心开发移至私有代码库；LangSmith 的旧合并 SDK 仓库已归档，Python 和 JavaScript SDK 分拆到独立仓库。不能把旧仓库归档直接理解为整个服务停止。

### 4.8 行业 Agent：领域结果不能靠通用榜单代替

[TradingAgents](https://github.com/TauricResearch/TradingAgents)、[AI Hedge Fund](https://github.com/virattt/ai-hedge-fund) 和 [Biomni](https://github.com/snap-stanford/Biomni) 是领域探索样本。AI Hedge Fund 明确定位为教育研究概念验证，不是实盘投资成效证据；Biomni README 提醒模型生成代码的执行权限和隔离要求。

这些项目证明某种实现路线被公开探索，不证明投资回报、临床有效性或真实科研任务能够无人负责地完成。垂直领域的价值需要对应专家、数据、流程和失败成本来判断。

## 5. 需求证据：采用、使用与授权意愿

### 5.1 中国市场：用户基础已经很大，但缺少独立 Agent 普及率

CNNIC 2026-10-10 的官方发布说明：截至 2026 年上半年，中国生成式 AI 用户规模突破 7 亿人，普及率超过 50%。**这是生成式 AI 的用户基础，不能改写成 7 亿 Agent 用户，也不能据此计算某款个人助手的可触达市场。** 本次未取得报告全文及其完整抽样细节。[CNNIC 原文](https://www.cnnic.org.cn/n4/2026/1010/c326-11714.html)

### 5.2 大众行为：信息、工作、创作和日常辅助都有使用证据

Pew 在 2026-02-17 至 02-23 调查了 5,119 名美国成年人，报告于 2026-06-17 发布。49% 表示使用过 AI 聊天机器人，24% 每天使用。以下用途的分母为美国成年人，工作一项例外：

| 使用用途 | 比例 | 分母 / 注意事项 |
| --- | ---: | --- |
| 搜索信息 | 42% | 全部受访成年人 |
| 工作任务 | 38% | 仅在职成年人，不能和其他行直接比较为同一总体 |
| 娱乐 | 25% | 全部受访成年人 |
| 生成或编辑图片、视频 | 24% | 全部受访成年人 |
| 获取医疗建议 | 20% | 描述已发生的使用，不证明回答安全或有效 |
| 饮食与健身信息 | 20% | 不等同于持续执行健康计划 |
| 获取新闻 | 13% | 不等同于独立核验事实 |
| 情绪支持或建议 | 10% | 不等同于治疗效果 |
| 陪伴 | 4% | 不等同于所有个人化互动 |

这是多选用途，比例不可相加，也不能当成中国需求排序。[Pew 原始报告](https://www.pewresearch.org/internet/2026/06/17/americans-and-ai-2026-chatbots-smart-devices-and-views-on-impact/)

另一项 NBER 工作论文研究截至 2025 年 7 月的 ChatGPT 消费端使用：非工作用途超过七成；实用指导、信息搜寻和写作合计接近八成。它支持将生活和非编程工作纳入调研，但研究对象是消费端对话，不是自主 Agent 的执行记录。[NBER 34255](https://www.nber.org/papers/w34255)

### 5.3 企业端：采用持续扩展，组织规模和成本影响落地

McKinsey 2026-08-25 报告的调查覆盖 97 个国家、1,719 名受访者，调查期为 2026-05-04 至 06-08。年收入超过 10 亿美元组织的受访者中，40% 报告正在扩展 Agent 部署；较小组织为 22%。约两成受访者称 AI 运营成本限制了使用。以上是自报调查，不是独立生产审计，也不代表企业整体已经获得相应收益。[2026 报告](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)

Docker 2026-02-20 发布的专业样本调查摘要称，60% 的受访组织已有 Agent 进入生产；样本为 800 多名开发者、平台工程师和技术决策者。这个数字不能与 McKinsey 的“扩展部署”直接比较：样本选择和采用阶段的定义不同。[Docker 原始摘要](https://www.docker.com/blog/state-of-agentic-ai-key-findings/)

### 5.4 自动执行：用户愿意接受的帮助方式并不相同

YouGov 2025-12-04 对 1,287 名美国成年人开展加权在线调查，2026-01-02 发布：65% 对 AI 比价持信任/接受态度，14% 对 AI 代为下单持相同态度。两项来自同一调查，可以说明不同动作的态度差别，但都不是实际使用率或付费转化率。[原始方法与结果](https://yougov.com/en-us/articles/53808-american-trust-in-ai-for-retail-consumer-sentiment-in-2025)

**产品含义是推断：** 大众产品可以先完成资料收集、比较和草稿，再为下单、发送、删除等动作提供明确复核。不同动作分别授权，比要求用户一次接受全部自主性更容易形成可理解的使用过程。

### 5.5 效果：助手有效，不等于所有环节应自动化

NBER 一项覆盖 66 家企业、7,137 名知识工作者的随机现场实验，在 2025 年 11 月修订摘要中报告：实验后半段实际使用集成式工具的受试人员，每周处理邮件的时间约少 2 小时。这说明进入现有办公入口可能产生实际收益；不能据此承诺另一款完整 Agent 有相同收益，也不能把使用者结果直接当作所有被随机分配人员的平均效果。[NBER 33795 修订摘要](https://www.nber.org/papers/w33795)

这些资料共同支持“需求存在、行为有差异、执行授权有门槛”。它们尚不能回答某个新产品的留存率、付费意愿或可实现利润。

## 6. 30 个大众需求场景

这里的“需求”分为两层：**上层活动存在调查或现成工具依据，具体 Agent 闭环仍是待验证假设。** 例如，Pew 证明有人使用 AI 获取饮食信息，并没有证明用户会维护家庭库存或愿意为采购 Agent 付费。

表中的人群与频率是场景分析，尚未经本次行为日志验证。“信息搜索、创作、娱乐、医疗使用”等指向 Pew 的大类；“写作/实用指导”也参考 NBER；“购物态度”指 YouGov；“既有工具”只证明有相应产品覆盖，不证明市场规模。

| 编号与需求 | 使用者与可能频率 | 理想的任务闭环 | 合适的产品/自动化方式 |
| --- | --- | --- | --- |
| **C01 信息查找与办事解释** | 全体用户；临时/高频 | 提出问题→查证当前来源→比较冲突→给出带出处的答案 | 问答或研究Agent；以来源核验为终点 |
| **C02 订阅信息与机会追踪** | 有固定主题的人；周期 | 指定来源/条件→检查变化→去重→只推送相关变化→记录是否有用 | 定时规则+Agent判断；发送范围需用户定义 |
| **C03 个人资料与凭证整理** | 资料较多的人；周期 | 主动导入→识别归属→提取日期/编号→关联事项→可以回到原件 | 文档工具+Agent；关键信息可修正 |
| **C04 文件与下载目录整理** | 电脑重度使用者；周期 | 识别重复/过期/未归档→提出整理方案→预览→执行→可恢复 | 规则为主，Agent辅助分类；删除另行确认 |
| **C05 购物比较与选择** | 有明确购买需求的人；低频但可能高价值 | 预算和约束→查当期价格规格→筛选→解释取舍→保留决定 | 研究Agent；用户确认购买 |
| **C06 订单、退换与保修事项** | 网购家庭；事件触发 | 导入凭证→核对平台条款与日期→找缺失证据→整理材料→跟踪完成 | 事项Agent；提交由用户复核 |
| **C07 家庭账单与预算复盘** | 愿意提供账单的人；周/月 | 导入→识别交易→用户纠错→汇总预算→解释异常→下期复盘 | 财务软件+Agent；金额按原始记录核对 |
| **C08 续费、到期与重复订阅** | 有订阅/证件的人；周期 | 登记依据→计算提醒节点→收集处理选项→用户决定→标记结果 | 大部分用规则；Agent处理复杂说明 |
| **C09 旅行规划与途中调整** | 旅行者；低频集中 | 确定人数/预算/约束→查可用信息→排程→发现冲突→调整→保留订单关系 | 规划Agent；预订和退款由用户确认 |
| **C10 周末活动与本地服务选择** | 家庭、朋友小组；周末 | 时间地点与偏好→筛选活动→确认营业/余位→形成可执行路线 | 研究Agent+日历；可用性必须复查 |
| **C11 菜单与采购清单** | 经常做饭的人；日/周 | 偏好和真实库存→拟菜单→合并采购→实际采购后更新→反馈剩余 | 食谱/库存工具+Agent；输入成本决定收益 |
| **C12 食品及家庭库存** | 愿意持续记录的家庭；日/周 | 入库→消耗/临期→建议先用什么→调整采购→校正数量 | 规则与条码优先；Agent解释搭配 |
| **C13 家电、维修与家庭保养** | 有设备维护任务的人；事件触发 | 识别型号→找正确说明→补充信息→列检查步骤→预约人工→留记录 | 检索Agent；危险操作交专业人员 |
| **C14 家庭事务与多人协调** | 多成员家庭；周/事件 | 收集待办→识别冲突→提出分工→成员确认→跟踪变更 | 共享待办+Agent；成员授权分开 |
| **C15 课程学习与概念辅导** | 学生、自学者；学习期高频 | 定位不懂之处→解释和练习→检查答案→调整难度→复测 | 教学Agent；不能只生成标准答案 |
| **C16 语言精听、表达与纠错** | 语言学习者；日/周 | 选材料→实际作答→定位错因→针对练习→新材料复测 | 训练Agent；转录错误不计为学习错误 |
| **C17 考试与证书准备** | 有明确考试的人；阶段高频 | 梳理范围→诊断薄弱项→安排练习→检查迁移→调整计划 | 训练Agent+题库；检查题目和资料版本 |
| **C18 求职材料与面试准备** | 求职者；阶段高频 | 收集真实经历→匹配要求→修改材料→模拟追问→记录反馈 | 文档/训练Agent；不虚构经历、不默认代投 |
| **C19 日常沟通与事务写作** | 普通职场人与家庭；高频 | 明确对象与目的→使用真实材料→草稿→用户修改→复用表达 | 助手通常足够；发送时再审批 |
| **C20 会议或课程后的行动整理** | 会议/课程密集者；工作日 | 授权笔记→提取决定→核对责任和日期→形成待办→追踪 | 整理Agent+任务工具；区分推测和承诺 |
| **C21 长文、故事与自媒体创作** | 创作者；周/项目 | 素材→结构→草稿→事实检查→编辑反馈→版本对照→交付 | 创作Agent；发布与素材权利另核对 |
| **C22 图片、音乐短片与视频制作** | 创作者、兴趣用户；项目制 | 作品目标→分镜/素材→初稿→按片段反馈→局部重做→导出 | 创作Agent+时间轴；记录费用和版本 |
| **C23 相册与个人素材管理** | 照片视频较多的人；周期 | 授权导入→搜索事件/人物/文字→整理候选→人工核对→相册 | 现成素材工具优先；Agent处理跨素材任务 |
| **C24 兴趣、游戏与个性化娱乐** | 有具体兴趣的人；日/周 | 发现内容→解释规则/知识→组织活动或创作→记住明确偏好 | 聊天通常足够；变化追踪再用Agent |
| **C25 运动、饮食与习惯执行** | 愿意持续记录的人；日/周 | 目标→可执行计划→实际记录→调整→回顾 | 记录工具+辅助Agent；核对真实执行 |
| **C26 就医资料整理与问题准备** | 有就医事务的人；事件触发 | 整理检查/病史→标不清字段→准备问医生的问题→管理复诊 | 资料Agent；诊断治疗由专业人员负责 |
| **C27 长辈及无障碍办事辅助** | 需要简化操作的人；事件/高频 | 语音输入→解释步骤→大字确认→协助填写→人工接手 | 语音/界面辅助；重要动作明确授权 |
| **C28 情绪表达与陪伴** | 有表达需求的人；频率差异大 | 表达→澄清需求→支持性回应→协助安排现实支持和日常行动 | 支持性对话；不承诺治疗效果 |
| **C29 申请、报销与公共事务材料** | 有手续需求的人；低频但繁琐 | 查官方要求→核对材料→发现缺项→草稿→用户提交→记录回执 | 材料Agent；版本、身份与回执需核实 |
| **C30 个人目标与计划回顾** | 愿意复盘的人；周/月 | 目标→具体行动→实际完成情况→解释阻力→调整计划 | 任务工具+Agent；避免只生成新计划 |

证据对应：C01/C02/C03/C09/C10 参考信息搜索；C05 参考购物态度；C07/C11/C12/C23 参考既有工具；C15/C16/C17/C30 参考实用指导；C18/C19/C21 参考写作与指导；C20 参考工作用途；C22 参考图片视频；C24 参考娱乐；C25 参考饮食健身；C26 参考医疗使用；C28 参考情绪支持与陪伴。C04/C06/C08/C13/C14/C27/C29 在本次没有独立量化证据。**全部 30 个具体产品闭环均标为 H，不能当成已证实的付费需求。**

### 大众化不等于同一个产品服务所有人

- **学习者和求职者**有阶段性目标，适合通过练习表现、材料完成和模拟面试检验价值。
- **家庭事务管理者**需要关联凭证、成员、日期和实际处理状态；输入是否持续可得比模型口才更关键。
- **普通职场人**更可能需要在已有文档、会议和消息入口里减少重复动作，而不是维护新系统。
- **创作者**关注可编辑性、风格控制和局部返工，单次生成效果不足以决定持续使用。
- **长辈与需要辅助的人**更依赖清晰提示、人工接手和可理解确认；安装配置门槛可能阻止使用。
- **技术用户**可能愿意自托管、配置工具与模型，但这个群体不能代表全部大众。

这些分组用于组织验证，没有据此估计各群体人数或消费能力。

## 7. 12 类生产与组织需求

企业购买的通常是更快处理、更少出错、更容易协同和更低总成本。下面是由采用情况与现有软件流程推导的任务地图，**不代表每类都已规模化部署**；本次没有逐个行业开展访谈。

| 领域 | 需要完成的闭环 | 关键数据/系统 | 应衡量的结果 | 主要边界 |
| --- | --- | --- | --- | --- |
| **客服与售后** | 知识与订单查询→确认问题→允许的处置→处理例外→转人工 | 知识、工单、订单及权限接口 | 解决率、重开率、转人工质量、每单总成本 | 真实政策与不可重复退款 |
| **销售与客户运营** | 整理线索→核验资料→跟进草稿→人工确认→更新CRM | CRM、授权资料、沟通入口 | 有效线索、跟进完成率、投诉、实际成交贡献 | 错误承诺与外发授权 |
| **内容与营销** | 收集主题素材→生成版本→事实/品牌审核→排期→复盘 | 素材库、品牌规范、渠道数据 | 可用内容率、审稿时间、实际触达或转化 | 发布审核与素材权利 |
| **财务与报销** | 收凭证→匹配单据→标异常→补材料→复核入账 | 凭证、规则、ERP、审计记录 | 错配率、复核时间、重复处理和返工 | 金额、身份、审批与账务一致 |
| **人力与内部服务** | 回答制度问题→收材料→核对缺项→启动流程→交接 | 制度版本、人员目录、HR系统 | 服务周期、一次补齐率、升级率 | 人员信息与重要人事决定 |
| **IT服务台与运维** | 识别故障→查依据→只读诊断→拟操作→审批执行→验证 | 工单、资产、日志、变更和手册 | 恢复时间、错误变更、回滚/接手情况 | 凭据范围与变更验证 |
| **数据分析与经营汇报** | 澄清指标→权限查询→检查口径→分析→可追溯结论 | 受治理的数据源与指标定义 | 正确率、校验时间、错误结论率 | 分母、时间窗和数据权限 |
| **合同与专业材料辅助** | 检索条款→对照模板→标差异→准备问题→专业复核 | 受控版本资料、模板与案例 | 漏项、误报、复核时间和可追溯性 | 专业责任与审签 |
| **采购与供应商协同** | 读需求→查供应→比价→澄清条件→待审采购单 | 采购、供应商、库存、审批系统 | 询价周期、信息完整性、异常发现 | 价格时效、供应身份与支付权限 |
| **物流与供应链异常** | 发现延期/缺货→查依据→替代方案→人工选定→回写 | 库存、运输、订单与约束 | 异常响应、缺货损失、调整成本 | 实时数据和跨系统一致性 |
| **制造与设备维护辅助** | 读取资料告警→查手册→检查建议→交接操作员→记录 | 资产、手册、工单、批准的数据接口 | 停机时长、误报、检修准备和记录 | 软件建议与物理控制分开 |
| **科研与行业知识工作** | 定任务→搜证据/专用工具→查结果→可复现材料 | 专业数据、工具、专家、执行隔离 | 可复现率、专家复核、失败成本 | 领域有效性和数据许可 |

### 企业和个人的差别在哪里

**企业往往有明确的流程所有者和验收对象。** 订单、工单、凭证和变更单可以成为 Agent 的工作对象，也便于追查错误。跨系统权限、历史数据质量与例外流程则增加实施成本。

**大众的单次需求可能真实，但未必适合独立订阅。** 一次旅行、偶发保修或临时写作，可能更适合通用助手、按次服务或嵌入现成工具。学习、周期复盘和长期事务有机会形成持续状态，但仍需验证输入成本。

**中小企业也不是简化版大型企业。** 没有稳定数据源、明确流程和维护人员时，复杂多 Agent 系统可能增加负担。起点可以是一个重复发生、人工能够检查的小流程。这是实施判断，不是对全部中小企业的调查结论。

### 实体生产中的适用范围

软件 Agent 可以协助手册检索、工单整理、异常解释和排程方案；设备控制、机器人运动和工艺参数闭环还需要现场工程、传感器、控制系统及对应验证。软件演示或 GitHub 热度不能证明物理生产安全、质量或停机收益。

| --- | --- | --- | --- |

## 9. 什么时候需要 Agent

| 任务特征 | 优先考虑 | 原因 |
| --- | --- | --- |
| 一次性、输入完整、只要文字或图片 | 通用助手 / 生成工具 | 长期运行和工具配置未必产生收益 |
| 条件确定、步骤固定、规则可维护 | 普通程序 / 工作流 / RPA | 结果更容易预测和测试 |
| 主要难点是批量查找和整理 | 数据库、OCR、检索、素材管理 | 先解决资料获得和可查询性 |
| 输入不完整、来源冲突、需选择下一步 | 有界Agent | 动态判断和补充材料可能减少组织工作 |
| 跨系统、有中间状态和失败分支 | 工作流+Agent+人工复核 | 需要执行、恢复和接手方式 |
| 同类任务持续发生、个性化状态重要 | 有业务状态的专用应用 | 价值来自业务对象与持续反馈 |
| 涉及外发、金钱、重要资料变更 | 可审阅草稿+明确确认 | 用户能看到对象、内容、金额及结果 |
| 行业判断或物理动作影响重大 | 专业人员负责的辅助系统 | 需要领域依据与真实环境验证 |

**一个实用检验：把大模型拿掉后，用户仍然需要这个业务对象吗？** 订单事项、练习记录、分镜版本、工单和采购单仍然存在。若答案肯定，产品至少有明确的组织对象；若只剩聊天框，需要进一步证明为什么用户不会直接使用已有助手。

**另一个检验：Agent 的判断到底减少了哪次人工操作？** 如果用户仍要逐项找资料、复制结果、检查每一步并重新执行，那么系统可能只改变入口，没有减少总成本。

多 Agent 仅在任务可分解、角色信息或工具权限确实不同、并行收益大于协调成本时才值得使用。角色数量本身不是用户结果。

## 10. 产品机会的条件式排序

按“能否拿到持续输入、完成边界是否清楚、结果能否检验、与现有工具的差异”作定性筛选。**这是本报告的判断，不是市场份额、付费意愿或成功概率排名。** 没有明确目标用户和数据入口时，不能直接变成研发结论。

| 候选 | 先验证的条件 | 可能形成的持续价值 | 最容易失败的地方 | 判断 |
| --- | --- | --- | --- | --- |
| 一类文件/凭证驱动的个人事务 | 用户反复查同类资料，愿意主动导入 | 资料、日期、待办与结果关联 | 录入纠错比查资料更费时 | 有真实样本时优先 |
| 固定岗位的文档/会议后续事务 | 已有工作流与复核人 | 材料推进为行动及可追踪状态 | 听错、责任不明、待办没人用 | 有组织入口时优先 |
| 窄目标学习训练 | 有连续练习者和可检查答案 | 诊断、练习、复测和训练记录 | 只生成计划，不能衡量表现 | 有持续使用者时优先 |
| 一类中小企业内部流程 | 已有负责人、规则和数据 | 减少重复收集、查询、补材料 | 接入成本高，例外不清 | 有试点客户时优先 |
| 创作与局部返工 | 经常制作同类作品 | 版本、素材、反馈与重做范围 | 成本高、审美不稳、无法局部改 | 适合明确创作人群 |
| 垂直研究与信息追踪 | 来源明确，用户会复核 | 可追溯结论、持续更新 | 权限、引用、已有工具足够 | 有专门资料优势再做 |
| 现有Agent的团队管理 | 已使用多个执行器 | 任务、权限、预算与审阅统一 | 实际没有协调负担 | 针对团队验证 |
| 生活常驻总助手 | 有自然入口与稳定多类任务 | 跨任务记忆、持续状态、提醒 | 任务太散、授权大、维护难 | 小团队谨慎起步 |
| 无人购物与资金操作 | 可信执行和清晰责任 | 减少交易操作 | 授权意愿、误买、重复支付 | 不宜作默认大众入口 |
| 金融/医疗完全自主判断 | 专业机构和专门验收体系 | 按具体专业流程判断 | 后果、责任、数据及验证门槛 | 不按通用助手路线立项 |

### 对个人开发者或小团队的含义

起点宜收敛为：**一类人、一种反复发生的任务、一组能获得的数据、一种可检查的完成结果。** “精听纠错与复测”比“学习生活全能助手”容易验证；“售后材料与事项”比“自动管理全部消费”容易设定边界。

已有模型适配、文件、任务恢复或审批能力可以降低实现成本，但不能代替需求证据。即便已有通用 Agent 代码，也应先确认业务对象与入口，再决定复用范围。此次调研不构成现有项目改造、迁移或发布授权。

## 11. 从演示到日常使用的关键约束

### 输入获得

日历、凭证、账单、库存和练习表现能否持续获得？手动上传也可以成立，但必须测量维护成本。用户说“我想自动管理”，不代表愿意每天补数据。连接平台应分别验证账号授权、可用接口、读写范围和地区条件。

### 结果核验

任务需要可观察终点：资料齐全、草稿可用、工单关闭、文件写入、付款回执或训练复测。只有模型声称“已完成”，无法建立可靠体验。不同任务需要不同证据，不能统一以总结代替。

### 失败与人工接手

真实使用会有资料缺失、登录失效、页面变化和服务失败。产品需要让用户看清已做什么、停在哪里、哪些动作没有发生、如何继续。保存必要恢复状态，比无限重试有用。

### 长期记忆

记忆可保存明确偏好、业务对象和历史，但应能查看、更正和删除；推测不能悄悄升级为事实。README 中的“会学习”是设计声明，长期准确性、错误传播与复用收益仍需验证。

### 经济性

应核算：**每个成功任务的总成本 = 模型与外部服务 + 运行成本 + 失败重试 + 人工复核与纠错 + 接入维护的合理分摊。**

这是建议的核算结构，不是测得的报价或收益。还需区分产品方成本和用户时间，防止把人工投入转移给用户。

### 授权与信任

分别呈现只读查询、生成草稿、可撤销修改和外部执行。关键动作确认时应让用户看到具体行为。不同动作的接受度有调查依据，但本次尚未验证哪种确认设计转化更高。

### 分发与维护

自托管、桌面、移动端、聊天入口和企业系统各有安装、通知、持续运行与升级条件。已有入口可能减少切换，需要实测。项目能启动、测试通过、有人部署和普通用户长期使用，是不同结论。

## 12. 如何把调研转成可验证决策

本次没有招募、访谈或真实账号试验。以下说明还缺什么证据，不代表已完成验证。

### 先看近期真实任务

对候选人群，收集近期确实发生的任务：输入是什么、现在怎样做、耗时在哪里、发生过什么错误、是否重复。不要只问“有一个 Agent 你会不会用”。偶发高价值事务按事件检验，训练与办公按持续使用检验。

### 用同一任务比较完整做法

比较原有方法、现成工具/通用助手和候选窄流程。使用同一材料和相近验收标准，记录准备、执行、复核及返工。不能只比较第一份输出速度，不能隐去用户补输入的时间。

| 需要知道什么 | 合适的观察 | 容易误用的替代指标 |
| --- | --- | --- |
| 任务是否完成 | 达到约定结果的比例及失败原因 | 模型回复“完成”的次数 |
| 是否省操作 | 准备+执行+复核+返工的总时间 | 第一份答案速度 |
| 是否可靠 | 错误类型、后果、能否发现 | 少量成功截图 |
| 是否继续用 | 同类任务再出现时主动使用 | 一次试用好评 |
| 是否愿意付费 | 真实购买/续用选择及当前支出 | 口头感兴趣 |
| 是否可持续交付 | 每个成功任务成本与维护投入 | 单个Token价格 |
| 自动化是否合适 | 接受、拒绝、纠正和接管的动作 | 工具调用或Agent数量 |

没有基线时，不编造统一成功率、留存率或价格门槛。标准应依据错误后果与当前做法；高频任务和低频事务不能套同一留存口径。

出现“持续给输入、任务反复发生、总操作减少、结果可核验”的证据后再扩大；若只适合部分步骤，就保留辅助工具；现成软件足够或维护输入超过收益时，应停止扩张。决定不开发也可以是有效结果。

## 13. 局限与尚未回答的问题

1. **数量：** 主题计数不是去重总量；54 个样本没有随机性，不报告类别份额或集中度。
2. **维护：** API归档标志与维护公告可能不同；push可能来自机器人；未逐一验证发布节奏和问题解决率。
3. **功能：** 16 个重点README有补读，其余以元数据确认。没有运行项目，不给成功率或性能排名。
4. **人群：** Pew、YouGov 为美国样本；NBER 为特定产品；企业调查口径不同，均不能直接外推中国所有用户。
5. **时间：** 部分使用研究为2025年数据，已标明；仓库和动态报告页面后续会变化。
6. **需求：** 场景目录不等于全部高频或愿意付费；未做访谈、留存、转化及单位经济性验证。
7. **收入：** 缺少可比用户和收入分母，不估算TAM/SAM/SOM，不拿预测规模当可获得收入。
8. **访问：** CNNIC报告介绍页超时，使用官方同期新闻；NBER34255落地页403，使用可检索原始摘要，不宣称全文已读；Paperless-ngx文档403，未纳入已确认对照。
9. **执行：** 未安装这些项目、连接私人账户、访问生产数据或调用付费模型。真实接入、中文体验和成本仍待验证。

**最终判断：需求基础存在，供给已覆盖多个层次；更有价值的问题，是哪类用户愿意把哪项具体事务持续交给系统，以及系统能否以更少总投入完成它。** 这不要求把所有大众需求塞进同一款助手。
