# PrivateAgent 自用垂直方向调研

调研日期：2026-10-22（Asia/Shanghai）。

## 1. 结论与适用边界

用户已经使用 Codex、Claude Code 处理编码及多数临时任务，本次目标是寻找非编程、非通用助手、先服务个人生活的产品方向，不再围绕开发周边寻找新定位。

建议优先验证三类候选：**音乐短片制作、英语精听纠错训练、个人消费与售后事务管理**。这个顺序是结合历史交流线索和接入成本作出的判断，不是市场排名，也不证明用户目前存在这些高频需求。

目前还不足以决定改造整个项目。应先验证某个场景能否重复使用，以及现成工具是否已经满足需求；没有留下持续使用理由时，保留现有项目、暂缓转型也是合理选择。

本次只查阅公开官方产品页与文档，没有安装或登录这些产品，没有读取个人订单、账单、相册、邮箱或学习记录，没有执行真实模型调用。功能表是文档范围内的事实，实际效果、中文支持、地区可用性、费用、账号权限及完整接入仍需分别验证。文档未提到某项功能，不等于产品没有该功能。

## 2. 筛选标准

不以“通用模型理论上做不到”作为条件。专用产品的价值应来自以下可观察收益：

1. 有稳定的业务对象和长期状态，例如分镜版本、听力错因、购买事项。
2. 有用户反复执行的闭环，例如修改片段并重出成片、针对错误复测、处理到期事项。
3. 记录和数据能持续获得，维护输入的成本小于节省的操作。
4. 有合适的交互入口，用户不用每天重新组织提示词、文件和工具。
5. 能通过实际任务判断收益，而不只展示模型回答。

对先自用的项目，自己能持续提供材料、判断结果并愿意复用，比推测商业付费潜力更重要。

## 4. 候选一：音乐短片制作 Agent

### 明确的使用任务

输入一段音乐、确认过的歌词、角色或视觉参考，制作一段可播放的短片；用户对具体时间点提出意见后，只修改受影响的镜头，并保留其他已经认可的部分。

历史交流中曾出现“逐句贴合歌词配图、先看短片、按时间点修改”的明确偏好。如果兴趣仍在，这是目前个性化依据最强的候选，但本轮没有确认制作频率。

### 产品应负责什么

业务对象为作品、分镜、角色参考、素材版本、时间轴和修改意见。Agent 负责选择下一步：发现歌词时间不匹配时重新对齐；镜头不符合要求时生成或挑选替代素材；修改后重出相关预览并等待复核。

主界面应围绕播放、分镜、素材和时间轴组织。聊天可以录入意图，但不承担所有编辑交互。

已有工具已经提供自动歌词与合成基础，因此自建要验证的假设是：用户是否需要更适合自己的分镜与局部返工流程。不是断言其他产品缺少这些能力。

### 最小验证

选同一段 30～60 秒内容，完成一次初稿和两次指定片段修改。先复用已有素材或已授权工具，不因调研自动付费生成内容。

记录人工操作时间、修改涉及的镜头、无意改变的已确认部分、实际费用及用户对结果的选择。与现有编辑工具和当前使用方式比较。

如果只偶尔制作一次，现成工具加临时脚本可能已经足够。如果会持续制作，且重复准备和返工明显占用时间，再考虑产品化。

### 主要约束

角色一致性、镜头审美、中文歌词对齐和生成成本均需实测；现有任务恢复代码不能证明生成服务具有幂等性。先确认作品与素材的使用范围，再考虑任何发布功能。

## 5. 候选二：英语精听纠错训练 Agent

### 明确的使用任务

用户选一段自己想听懂的英文材料。系统安排短时精听、收集听写答案、区分可能的错因，针对错误安排练习，并在新的材料上复测。

这里的目标是训练结果，而不是再提供一个翻译器或生词本。历史上存在英语学习项目这一线索，但是否正在进行日常精听，仍待确认。

### 产品应负责什么

业务对象为材料、句子、答案、错因假设、训练记录和复测结果。Agent 根据表现决定下一步练习：词义不熟、已知词在连读中未识别、句法理解错误，处理方式应不同。

错因是可修正的判断，不能仅凭一次听写强行认定。转录错误也不能算成用户错误。第一版可只做听力与文本回答，不把发音评分作为前置范围。

Readlang 和 Migaku 已覆盖较多阅读、解释及制卡能力，Anki 可作为复习出口。因此必须先检验上述训练闭环是否给用户带来额外价值，而不是重新实现词卡系统。

### 最小验证

连续七天，每天使用一小段材料和固定的短时训练。人工复核部分错因，另用未练过的材料观察迁移效果。

记录实际使用天数、训练准备耗时、错因判断是否被用户纠正、复测表现。七天只能验证使用意愿与流程，不能据此宣称长期学习效果。

如果主要需求只是查词和积累词卡，应先使用现成工具。如果愿意训练，但练习组织和针对性反馈持续构成障碍，才值得扩展。

## 6. 候选三：个人消费与售后事务 Agent

### 明确的使用任务

将用户主动导入的购买凭证、订单截图、售后说明和产品资料关联为一个购买事项，追踪缺失资料与待处理事件；需要售后时，整理已有证据和下一步清单。

第一版不要求直连电商、邮箱或支付账户，也不读取登录态。用户尚未说明此类事项的数量与处理负担，所以该方向的需求依据弱于前两项。

### 产品应负责什么

业务对象为购买事项、商品、凭证、日期依据、待办与处理结果。每个重要日期和金额必须能定位到来源；来源冲突或识别不清时请求核对，不凭通用常识补成确定结论。

已有 OCR 和文档管理工具解决的是部分输入及归档问题。自建的假设是：关联这些资料并跟踪事项，能否减少查找和遗漏。Paperless-ngx 也有工作流，所以不能把“会提醒”本身当成独有价值。

### 最小验证

用一组用户主动选择的购买记录，测试关联、查询、日期核对及一次售后资料整理。比较录入和纠错成本与查找节省的时间。

如果维护输入比实际节省的操作更多，或几个月才发生一次，应优先保留为轻量工具，而不是改造整个 Agent。

## 7. 当前不优先的方向

- 通用个人知识库、资料总结、万能生活助手：仍然容易回到通用模型的临时问答范围。
- 从零重做相册、记账、食谱和库存系统：已有产品覆盖较完整，先体验和接入更有依据。
- 面向商家的订单、采购和售后产品：可能存在明确流程，但用户当前选择先自用，也没有提供行业样本或试用用户，不能据此优先立项。
- 单靠提醒、自动分类或自然语言入口：这些能力可以是配套，尚不足以单独证明转型价值。

## 8. 对现有项目的处理建议

先验证业务闭环，再决定保留多少旧架构。模型适配、凭据管理、本机存储、附件、任务事件、取消和审批可以作为复用候选；不因为已有代码就保留不适用的复杂度。

若选择音乐制作，主要交互应变为作品与时间轴；若选择英语训练，主要交互应变为训练与掌握记录；若选择消费事项，主要交互应变为事项列表与证据。项目目录、补丁、代码差异和终端不应继续占据产品中心。

本次不制定数据库迁移、数据删除或代码重构计划，也不修改现有历史和用户配置。确认方向之前，不建议开展整仓改造。

## 9. 下一步的判断方式

优先用最近发生的真实任务验证，而不先建设新的通用框架。依次检查：

1. 这个任务是否实际重复发生；创作按多次返工检验，学习按连续训练检验，事务按实际处理数量检验，不套用同一个频率门槛。
2. 现成产品和当前使用方式还留下哪些具体操作负担。
3. 一个窄流程是否已经减少这些负担，且用户愿意主动再次使用。
4. 为维持状态和数据输入付出的时间，是否低于获得的收益。

只有上述证据出现，才把 PrivateAgent 转为对应产品。暂时没有合适的自用需求时，可以先保留项目，不必为了“Agent”名称强行开工。

## 10. 调研未覆盖的事项

本次没有穷尽市场产品，没有进行实际安装、中文材料质量对比、价格与配额核验、模型或显卡性能测试，也没有证明候选工作流在现成产品中不存在。

部分文档打开遇到 403 或超时，例如 Paperless-ngx 使用页、Homebox、Eagle 和 AniList；Paperless 的概览与搜索返回资料仅用于确认基础覆盖，其他未能充分取得内容的产品没有作为推荐的能力依据。Bangumi 搜索返回含 private API 的文档，不能据此承诺公共接入稳定性，本次未将其作为优先候选。

研究结论是下一步验证的假设，不是立项、改造、安装、访问私人数据、付费调用或发布授权。
