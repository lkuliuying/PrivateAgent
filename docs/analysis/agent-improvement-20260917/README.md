## 4. 三步执行顺序与里程碑

```mermaid
flowchart LR
  A[第一步：目标与约束] --> B[第二步：计划与长任务闭环]
```

| 里程碑 | 退出条件 | 交付物 |
|---|---|---|

## 5. 实施原则与兼容要求

1. **先正确，再提速。** 第一阶段先修意图和约束；第二阶段打通连续性；第三阶段才开启只读并行。
2. **复用现有主链。** 共享核心不依赖旧服务端数据库；本地持久化继续经 `LocalStore`；前端经既有事件投影消费状态。
3. **增量契约。** 新字段有默认值和版本解释；旧任务可读取；不凭模型建议自动改变数据库或公共接口。需要迁移时先给出受影响表、兼容和恢复方案，再在对应阶段执行最小迁移。
4. **证据决定验证状态。** 模型说“完成”、计划勾选、命令退出和用户目标满足是不同状态。成功测试还必须匹配当前工作区版本。
5. **审批不抵消禁止项。** 明确禁止的动作先被策略拦截；普通审批按钮不负责解除用户限制。
6. **恢复保留不确定性。** 已产生或可能产生副作用的操作，不因断线、暂停、失败或重启而自动重放。
7. **控制成本。** 默认不增加每轮独立的“解析模型”或“反思模型”；优先用结构化状态和确定性检查，新增模型调用需有明确收益及预算。

## 6. 验证与打包条件

第一阶段命令及观察结果见[第一步验证记录](./step-1-intent-and-constraints.md#9-2026-09-17-实施与验收记录)，第二步的源码验证见[本地编排实施记录](./step-2-planning-context-and-recovery.md#9-2026-09-20-本地任务编排实施记录)。第三阶段的完整交付仍须按其验收条件单独核对，不能用本次源码测试替代安装包或真实模型验收。

- 第一、二步以隔离单元测试、运行时契约测试和前端状态测试为主，避免付费模型调用。
- 第三步增加并发、取消、工作区边界、旧任务读取和打包脚本测试。真实模型试用由用户在自己的配置和授权下进行。
- 新测试加入现有验证脚本对应套件，避免只新增文件却未被固定用例列表执行。
- 改动直接涉及的权限、数据完整性、恢复及完成证据测试必须通过。出现失败先定位，不能交给用户试用代替修复。
- 较广回归根据影响范围执行。既有全量套件超时等问题单独记录，不能写成通过，也不以已取消的大规模质量评测作为本地试用的新增门槛。
- 构建前确认源码在验证后未继续变化；变化时重跑受影响验证。预览构建允许有未提交代码，但必须有准确的来源清单。归属不明且影响交付的改动需要先核对，必要时使用经审查的隔离构建副本；不得靠清理或回退现有工作区排除它们。
- 包装目标为当前 Windows x64 统一桌面候选版。使用独立候选身份、凭据范围和数据目录，记录未签名属性、版本、哈希和已知限制，不上传或触发线上更新。

具体命令、产物及退出条件见各步细则，尤其是[第三步交付流程](./step-3-capabilities-and-trial-delivery.md)。

## 7. 用户试用与迭代约定

完整三步候选仍按原顺序实施；第一阶段试用包已依用户后续请求提前交付。用户安装、试用并反馈；后续每个候选版本附本次修复、仍存在的问题和建议复测场景。

反馈最少包含：候选版本、操作步骤、预期行为、实际行为、是否稳定复现。可补充脱敏的任务编号、错误信息、截图和小型复现项目；不要求用户提供密钥、完整生产日志或私人项目内容。

| 优先级 | 判定 | 处理原则 |
|---|---|---|
| P0 | 越权执行、用户数据损坏、敏感内容泄露 | 暂停该候选版使用；隔离原因、修复并补边界回归后再交付 |
| P1 | 无法启动、主要任务无法完成、卡死或恢复导致重复副作用 | 优先复现和修复，作为下一候选包的必要项 |
| P2 | 进度或结果不清、局部性能问题、可绕过的兼容问题 | 与具体场景绑定，在后续小批次修复 |
| P3 | 新能力或体验偏好 | 进入待选清单，避免挤占可靠性修复 |

每条反馈记录“待复现 → 已定位 → 修复中 → 自动回归通过 → 已交付待复测 → 用户确认/仍复现”。没有用户回执时，只标记已交付或自动验证通过。
