## 1. 版本决策

### 1.1 执行结论

本次改造作为集成开发列车中的独立UI检查点执行，不再等待 `0.3.0` 观察或正式发布。`0.4.0` 不单独发布稳定版，而是在 `alpha.1` 和 `alpha.2` 两个内部节点完成全部UI能力，然后直接把新工作台交给 `0.5.0` 可信执行开发复用。

主线版本安排：

| 版本 | 主题 | 核心边界 |
|---|---|---|
| `0.3.0-alpha.2` | Runtime能力冻结 | 已完成执行链、恢复、验证、RAG、摘要、安装升级和公开契约冻结 |
| `0.4.0-alpha.1` | 设计系统与应用壳 | D0–D2：UI审计、令牌、基础组件、UI Lab、导航和三栏壳 |
| `0.4.0-alpha.2` | Workbench UX 2.0完成 | D3–D6：Agent核心流、全部业务页面、动效、无障碍、性能和安装验收 |
| `0.5.0-beta/rc` | 可信执行与集成冻结 | 在新工作台中接入有界代码、命令、API、只读SQL和多步骤工作流 |
| `0.6.0+` | 外部与平台扩展 | MCP深化、远程Provider、跨平台、签名和更多集成 |

### 1.2 前置条件已经满足

以下进入条件已在 `0.3.0-alpha.2` 完成，不再作为等待项：

1. Chat Runtime、取消、审批、RAG、断线恢复和摘要契约已经冻结；
2. Python、Vue、Tauri和Cargo版本已统一，完整release-check为14/14；
3. 开发环境与安装版M0均完成真实模型、reconcile、owner lock和SHA绑定；
4. `0.2.1 → 0.3.0-alpha.2` 覆盖安装、数据保留和回滚路径通过；
5. 公开UI契约已记录在 [`v0.3.0-public-contracts.md`](./v0.3.0-public-contracts.md)，12项契约测试通过；
6. 当前主线工作区干净，可从 `e6da3ee` 直接建立UI开发基线。

因此D0可以立即开始，D1–D6无需等待额外观察天数。

### 1.3 为什么保持独立UI检查点

本次工作包含导航、布局、组件契约、动效系统和交互模式变化，用户能明显感知，测试和回滚范围接近一个完整功能版本。独立检查点可以冻结UI契约、保留renderer回退，并避免与 `0.5.0` 的高风险工具能力混为一次变更。

### 1.4 为什么应早于可信执行工作流

代码Diff、终端运行、审批、失败恢复和产物管理都依赖清晰的状态呈现。如果先在旧界面上接入 `0.4.0` 原计划中的可信执行，再重做UI，会产生两次组件和E2E改造。先交付 Workbench UX 2.0，可以让 `0.5.0` 直接复用新的活动流、审批卡、Diff、产物栏和任务状态模型。

## 2. 当前前端基线

### 2.1 已有资产，应保留演进

项目并非从零开始，现有基础包括：

- `WorkspaceShell` 已具备左侧导航、中央工作区、可折叠检查器和状态栏；
- `NavRail` 已具备主导航、最近任务、折叠和快捷命令入口；
- `tokens.css` 已统一基础颜色、字号、间距、圆角、阴影、动效和布局尺寸；
- `components.css` 已提供按钮、输入、徽标、状态点和卡片 primitive；
- 已使用 Phosphor Icons，图标风格可以保持一致；
- 已引入 anime.js，并实现作用域清理及 `prefers-reduced-motion`；
- 已有Vitest 32项、Playwright 15项和Tauri/sidecar smoke基础，当前完整release-check为14/14；
- 已存在1280px附近、1600px和窄窗口截图证据；
- Agent活动、审批、任务计划、检查器、通知、命令面板等组件已经具备真实业务接口。
- `api/`、`animations/`、`design/`、`models/`、`stores/` 和 `dev/` 已形成初步模块边界；
- `0.3.0-public-contracts.md` 已冻结capabilities、SSE、run状态、审批、RAG来源和摘要元数据，可作为UI唯一后端事实源。

这些资产应作为2.0设计系统的迁移起点，而不是全部删除后重写。

### 2.2 当前主要问题

#### 信息架构

- 当前存在十余个一级视图，主要入口与“更多工作区”之间的分组仍偏功能清单，不完全符合用户任务心智；
- “任务”“Agent”“今日”“项目”“学习”“记忆”等概念边界需要重新梳理；
- 设置、诊断、备份、扩展等维护型页面与日常工作入口混在同一导航体系；
- 当前视图主要依赖 `App.vue` 中的 `view` 条件分支，页面元数据、返回历史和模块化迁移尚未统一；本版本优先建立类型化视图注册表，不额外引入Web Router依赖。

#### 视觉一致性

- 运行状态页已形成较强的青色玻璃感和大面积展示卡，而日常工作区更偏克制的生产力界面，页面气质存在断层；
- 部分页面使用大量卡片和装饰性区域，部分页面仍是传统表单或功能面板，密度、标题层级和留白不统一；
- 深色主题只有令牌脚手架，未达到可发布状态；
- 现有状态页更像展示型Dashboard，Agent日常工作的计划、执行、审批和结果还没有成为全局视觉中心。

#### 交互一致性

- 长任务的“正在做什么、下一步是什么、哪里需要用户处理”尚未形成跨页面统一语言；
- 空状态、加载、流式生成、重连、失败、停止、审批和完成状态由各页面分别表达；
- 右侧检查器只在聊天视图使用，文件、上下文、来源和产物尚未形成跨任务通用能力；
- 全局反馈虽已有Toast、确认框、通知中心和命令面板，但触发规则、层级和文案需要统一。

#### 动效

- 已有动效基础，但部分卡片悬停达到 `translateY(-6px) + scale(1.02)`，对高密度桌面工作台略显跳跃；
- 页面入场动画达到420–560ms，频繁切换页面时可能拖慢感知速度；
- 动效还没有按照“导航、反馈、状态、强调”建立语义级规范；
- 动态列表、SSE活动流、审批出现和任务完成需要比普通卡片入场更明确的状态动效。

#### 前端结构

- `App.vue` 同时负责启动、API协调、会话、Runtime兼容、视图导航和全局覆盖层，当前约1008行；
- `api.ts` 约2094行、`types.ts` 约1291行，虽然已有领域模块，但聚合入口仍然过重；
- `TodayView.vue` 约2057行、`LearningWorkspace.vue` 约1392行，业务状态与布局样式耦合；
- 基础组件覆盖面仍有限，页面中存在较多局部按钮、表单、卡片和状态样式；
- 当前没有独立的UI状态展厅，很多状态只能通过真实接口或特定数据才能复现。

## 3. 产品与设计目标

### 3.1 核心目标

`0.4.0` 要把 PrivateAgent 从“功能完整的多页面桌面工具”升级成“以任务执行为中心的个人Agent工作台”。

用户进入任意核心任务后，应能在数秒内回答：

1. 我现在在哪个工作上下文；
2. Agent正在做什么；
3. 当前计划和进度是什么；
4. 是否有错误、风险或待确认操作；
5. Agent读取、修改或生成了什么；
6. 我下一步最应该做什么。

### 3.2 设计原则

1. **任务优先**：突出目标、进度、阻塞和结果，不把所有内容做成聊天气泡。
2. **内容优先**：青色用于交互和状态，避免大面积高亮、霓虹和装饰性Dashboard。
3. **渐进披露**：默认显示人类可读摘要，日志、参数和技术细节按需展开。
4. **稳定可预期**：异步状态不跳动，不因工具调用或新活动导致阅读位置失控。
5. **本地可信**：文件、模型、数据库、授权和隐私状态以可理解的方式呈现。
6. **键盘友好**：高频操作可通过键盘完成，焦点路径清晰。
7. **动效有意义**：动效只解释层级、状态变化和空间关系。
8. **桌面优先**：首先服务Windows桌面窗口，同时保证窄窗口可完成核心流程。

### 3.3 非目标

`0.4.0` 不包含：

- 重写FastAPI、Agent Runtime、RAG或数据库模型；
- 新增代码、Shell、API和数据库高风险执行能力；
- 更换Vue、Tauri或重新引入一套大型UI框架；
- 为视觉效果引入多个重复动画库；
- 删除legacy API或改变 `0.3.0` 已冻结的状态语义；
- 把Windows桌面应用改造成移动端或公网多租户Web应用；
- 为所有功能同时设计手机布局。

## 4. 目标信息架构

### 4.1 一级导航建议

| 分区 | 入口 | 主要内容 |
|---|---|---|
| 日常 | 今日 | 简报、待办、提醒、收件箱和继续工作 |
| 执行 | Agent | 会话、计划、活动流、审批、结果和产物 |
| 工作 | 项目与任务 | 项目、任务、目标、代码工作区和学习工作流 |
| 知识 | 知识库 | 文档、集合、搜索、记忆和学习资料 |
| 连接 | 集成 | MCP、本地集成、扩展和Provider连接状态 |

维护入口放在导航底部的“系统”区域：

- 设置；
- 运行状态；
- 诊断；
- 备份与恢复；
- 更新与版本信息。

最终分组需在D0阶段结合现有页面和真实使用频率确认，但一级入口数量应控制在5–6个，不再把每个后端模块都直接变成一级导航。

### 4.2 全局工作台结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 左侧导航  │             中央主工作区             │ 上下文栏 │
│           │ 顶部：位置 / 标题 / 状态 / 主要操作  │ Files    │
│ 工作入口  │                                      │ Context  │
│ 最近任务  │ 计划、对话、活动、表格或编辑工作流   │ Sources  │
│           │                                      │ Artifacts│
│ 系统入口  │ 底部：输入 / 停止 / 模式 / 引用      │          │
├──────────────────────────────────────────────────────────────┤
│ 状态栏：后端、模型、同步、任务状态、版本                     │
└──────────────────────────────────────────────────────────────┘
```

布局建议：

- 左栏展开宽度224–240px，折叠宽度64–72px；
- 中央区域始终是视觉中心，并设置合理最小宽度；
- 右栏宽度320–360px，可切换 Files、Context、Sources、Artifacts；
- 低于1320px时右栏默认关闭，通过抽屉打开；
- 低于960px时左栏自动折叠，核心任务仍可完整操作；
- 三个区域拥有明确、独立的滚动边界；
- 底部输入区使用占位空间，不遮挡最后一条活动或消息。

### 4.3 页面层级

统一页面标题结构：

1. 面包屑或工作上下文；
2. 页面/任务标题；
3. 一行状态摘要；
4. 主要操作和次要菜单；
5. 页面主体。

运行状态页从大面积展示型Hero调整为紧凑系统页：突出异常、修复动作和最近变化；健康时不与Agent主工作区争抢视觉注意力。

## 5. 设计系统2.0

### 5.1 令牌结构

把当前单层变量升级为三层令牌：

1. **Primitive**：基础颜色、字号、间距、圆角、阴影、时长；
2. **Semantic**：背景、正文、弱正文、主操作、危险操作、焦点、运行、成功、等待；
3. **Component**：按钮、输入、导航、卡片、审批、活动、面板的具体令牌。

必须禁止页面继续新增无说明的十六进制颜色、任意字号和任意z-index。

### 5.2 色彩

- 保留冷灰白背景、白色表面、深青灰导航和青色强调；
- 降低大面积渐变和玻璃效果，将其限制到品牌区或少量关键状态；
- 成功、等待、危险、信息使用独立语义色，不能全部依赖青色；
- 文本与表面组合达到WCAG AA对比度；
- 先完整交付浅色主题；深色主题只有在全部核心页面通过验收后才能对用户开放。

### 5.3 排版

继续使用系统字体，避免打包大型字体资源：

```text
中文/界面：Segoe UI Variable / PingFang SC / Microsoft YaHei
代码/参数：Cascadia Code / Consolas / 等宽后备
```

建议语义字号：

| 角色 | 字号 | 字重 | 用途 |
|---|---:|---:|---|
| Display | 28–32px | 600–650 | 少量空状态或首次引导 |
| Page title | 22–24px | 600 | 页面、任务标题 |
| Section title | 16–18px | 600 | 页面分区 |
| Body | 14px | 400 | 正文和主要列表 |
| Compact body | 13px | 400–500 | 高密度元数据和次级列表 |
| Meta | 11–12px | 400–500 | 时间、状态和辅助信息 |
| Mono | 12–13px | 400 | 路径、命令、日志和Diff |

要求：

- 中文正文行高不低于1.5；
- 技术日志和代码区域使用等宽字体，但普通工具摘要不使用等宽字体；
- 避免全大写英文成为主要中文页面的层级手段；
- 标题、正文、元数据和链接必须有统一截断与换行规则。

### 5.4 间距与密度

- 继续使用4px基础单位和8px主要节奏；
- 页面外边距以20/24/32px为主；
- 卡片内部以12/16/20px为主；
- 同类列表项高度统一；
- 默认采用舒适密度；紧凑密度可作为后续设置，但不得在首轮同时维护两套布局。

### 5.5 基础组件清单

应建立可复用、可测试的 `pa-*` 组件，而不只共享CSS类：

- Button、IconButton、ButtonGroup；
- Input、Textarea、Select、Checkbox、Switch；
- Field、FormSection、ValidationMessage；
- Badge、StatusIndicator、Progress、Spinner；
- Tabs、SegmentedControl、Disclosure；
- Card、ListItem、DataRow、Toolbar；
- Dialog、ConfirmDialog、Popover、Tooltip、DropdownMenu；
- Toast、InlineNotice、ErrorState、EmptyState、Skeleton；
- SplitPane、Drawer、ResizablePanel；
- ActivityItem、ApprovalCard、ArtifactCard、DiffSummary；
- VirtualizedLog/长列表容器（仅在真实性能数据需要时引入）。

所有组件必须覆盖默认、hover、focus-visible、active、disabled、loading、error状态。

### 5.6 UI状态展厅

建立仅开发模式可见的UI Lab，集中展示：

- 所有基础组件及状态；
- Agent idle/running/waiting/completed/failed/stopped；
- 短文本、长文本、中文、英文、路径和日志；
- 空状态、加载、错误、离线和重连；
- 1280/1440/1920宽度状态；
- reduced-motion和高对比度检查。

UI Lab应复用真实组件和类型，不维护一套独立演示组件。

## 6. 核心交互改造

### 6.1 Agent任务工作区

中央工作区按照内容类型区分表现：

- 用户请求：简洁任务输入，不做过度气泡化；
- Agent解释：正文内容；
- 计划：独立步骤列表；
- 工具调用：动作摘要，可展开参数和结果；
- 审批：高优先级确认卡，明确影响范围；
- 文件修改：Diff摘要、文件数量、增删行和查看入口；
- 运行日志：折叠技术区域；
- 最终结果：高层级结果块和产物入口；
- 错误：原因、影响、已完成内容和恢复动作。

必须覆盖：

- 空任务；
- 正在规划；
- 流式回答；
- 工具执行；
- 等待审批；
- 用户拒绝；
- 用户停止；
- Ollama离线；
- sidecar断开和重连；
- 输出验证失败；
- RAG引用拒答；
- 断线后恢复；
- 任务完成和多产物。

### 6.2 审批交互

审批卡必须显示：

- Agent准备执行的动作；
- 对象、路径、服务或命令范围；
- 为什么需要授权；
- 风险等级和是否可撤销；
- 批准、拒绝和查看详情；
- 过期、已消费、失败和恢复状态。

批准后卡片原位转换为“已批准/执行中”，不得从活动流消失后在其他位置重新出现。

### 6.3 长任务与活动流

- 新活动到达时不强制抢走用户滚动位置；
- 用户处于底部时自动跟随，离开底部后显示“有新活动”入口；
- 状态变化更新原活动，不重复插入近似卡片；
- 计划步骤与活动流关联，点击步骤可定位对应活动；
- 默认折叠低价值日志，保留失败附近的诊断上下文；
- 停止按钮应立即产生视觉反馈，并区分“正在请求停止”和“已停止”。

### 6.4 右侧上下文栏

右栏统一为四类信息：

1. Files：授权文件、修改状态和Diff入口；
2. Context：会话上下文、模型、模式、限制和附件；
3. Sources：RAG来源、引用和可信状态；
4. Artifacts：文档、代码、图片、报告和导出结果。

右栏内容必须与当前任务绑定，不展示与当前上下文无关的全局信息。

### 6.5 导航和快捷操作

- 使用类型化视图注册表统一页面名称、图标、权限和快捷命令；
- 沿用当前 `View` 联合类型和 `view` 状态，抽取统一的视图注册表与导航服务；
- 使用轻量内部历史栈支持返回、前进、恢复上次视图和测试定位，不在本版本引入Vue Router；
- 页面需要定位具体对象时使用类型化导航参数，不在组件中散落字符串URL或自行解析hash；
- `Ctrl/Cmd+K` 保留为全局命令入口；
- `Ctrl/Cmd+N` 新建任务，`Esc` 关闭浮层或取消临时状态；
- 快捷键不能覆盖输入框的常见编辑行为；
- 最近任务支持键盘选择和清晰的运行状态。

### 6.6 启动与错误恢复

启动流程统一为：

```text
检查配置 → 启动sidecar → 检查能力 → 进入工作台
```

长于500ms才展示加载态，避免快速启动闪屏。失败页必须说明：

- 哪个依赖失败；
- 是否影响本地数据；
- 可以重试、重新配置、打开诊断或退出；
- 不向普通用户直接堆叠原始异常。

## 7. 动效系统

### 7.1 动效等级

| 等级 | 时长 | 用途 |
|---|---:|---|
| Instant | 80–120ms | 按压、颜色、轻量状态反馈 |
| Fast | 120–180ms | hover、focus、菜单和Tooltip |
| Standard | 180–240ms | 面板、页签、折叠和列表更新 |
| Deliberate | 240–320ms | 首次打开大型抽屉或任务完成状态 |

频繁页面切换不使用超过320ms的动画。

### 7.2 动效职责

- CSS transition负责按钮、输入、hover、focus和简单展开；
- Vue Transition负责页面、抽屉、列表和浮层生命周期；
- anime.js只负责Agent状态序列、计划推进和少量复杂编排；
- 所有anime.js作用域必须在卸载时清理；
- 不使用无限旋转或脉冲作为普通装饰；
- 运行状态可以有低振幅、低频率反馈，但不干扰正文阅读。

### 7.3 建议调整

- 卡片hover位移从当前6px降低到0–2px，不默认缩放整张高密度卡片；
- 页面入场改为短距离4–8px与淡入，避免每次导航重新表演完整首屏；
- 新活动进入使用120–180ms轻微淡入；
- 审批出现使用强调边框与一次性状态过渡，不使用持续闪烁；
- 完成反馈使用图标、状态色和一次性微动效，不使用粒子或大面积庆祝动画；
- 停止、失败和离线优先立即更新文本与操作，再执行退场动画。

### 7.4 Reduced Motion

当 `prefers-reduced-motion: reduce` 时：

- 移除位移、缩放、视差、循环脉冲和复杂时间线；
- 保留必要的瞬时颜色和可见性变化；
- Spinner改为静态进度说明或低运动替代；
- 功能、顺序和状态信息不能依赖动画才能理解。

## 8. 前端工程改造

### 8.1 目录建议

```text
src/
  App.vue               # 启动边界、视图出口和全局overlay
  api/                  # 继续拆分HTTP、SSE和Tauri适配
  animations/           # 动效语义与作用域清理
  components/           # 现有页面和工作区，迁移期保持可运行
  composables/          # 新增：流式、导航、快捷键、焦点和滚动行为
  design/               # 现有tokens.css、components.css和新增pa-*组件
  features/             # 仅在一个领域完整迁移时建立，不做半拆分
    agent/
    today/
    knowledge/
    projects/
  models/               # 面向UI的领域模型和状态映射
  stores/               # 跨页面状态，不存局部表单状态
  dev/                  # UI Lab、fixture和可复现场景
```

迁移采用逐页面方式，不进行一次性机械搬目录。现有 `api/`、`animations/`、`design/`、`models/`、`stores/` 和 `dev/` 直接演进；只有某个领域的组件、模型、状态和测试能够一次完整迁移时，才建立对应 `features/<domain>/`。

### 8.2 `App.vue` 拆分

`App.vue` 最终只负责：

- 应用启动边界；
- 类型化视图出口；
- 全局错误边界；
- Toast、Dialog、Command Palette等覆盖层。

以下逻辑应移出：

- 会话和消息状态；
- SSE生命周期；
- Runtime/legacy兼容模式选择；
- 审批动作；
- 视图标题映射；
- 页面级窗口和检查器行为。

拆分不以“文件越小越好”为目标，而以资源所有权清晰为目标：谁创建定时器、监听器、SSE或AbortController，谁负责在停止、切换视图和卸载时清理。

### 8.3 状态管理

- 优先使用领域composable和现有轻量store模式；
- `0.4.0` 默认不引入Pinia、Vue Router、Tailwind或大型组件库；确需新增依赖时必须先提交ADR并证明现有模式无法满足；
- 请求状态不得只用一个全局 `loading` 布尔值；
- 所有长任务状态基于后端事实和run id，不用纯前端计时伪造；
- 前端只消费公开状态，不推断或展示模型隐藏推理；
- 搜索、筛选、轮询和SSE并发必须采用AbortController、请求序号或最后一次请求获胜策略；
- 切换会话、视图和窗口关闭时必须清理旧SSE、轮询、监听器、动画作用域和临时文件选择状态。

### 8.4 兼容策略

- 保留 `0.3.0-alpha.2` 已冻结的 API 和事件类型；
- 使用适配层把legacy和Runtime事件映射到统一UI模型；
- 开发期保留renderer内部 `ui_v2` 或等价开关，按页面迁移；
- `0.4.0-alpha.1` 默认兼容页面，新壳按内部配置开启；
- `0.4.0-alpha.2` 内部安装包默认新UI，关闭开关可回到兼容UI；
- 双实现只保留到 `0.5.0-rc.1` 观察完成，物理删除另行评审；
- UI开关不改变后端数据和执行路径。

## 12. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| UI实现偏离已冻结Runtime契约 | 状态映射错误、恢复入口失真 | 只消费公开DTO和事件；契约变化必须先更新冻结文档与测试 |
| 一次性重写导致功能丢失 | 难回归、难回退 | 新壳先兼容旧页面，再逐页迁移 |
| 双UI长期并存 | 维护成本翻倍 | `ui_v2` 只保留到 `0.5.0-rc.1` 观察完成 |
| 过度追求视觉效果 | 信息密度下降、性能回退 | 内容优先、动效预算、视觉QA和性能门槛 |
| 页面组件继续各自定义样式 | 设计系统失效 | D1先完成基础组件，PR检查禁止新增散落令牌 |
| 动画与SSE更新冲突 | 抖动、滚动失控 | 状态更新优先，动画可取消且必须清理 |
| 导航重组让老用户迷路 | 学习成本增加 | 保留名称映射、首次提示和命令搜索 |
| 深色主题扩大范围 | 延期和对比缺陷 | 浅色主题先发布，深色主题独立门槛 |
| 截图好看但真实状态不可用 | 发布后暴露边界问题 | UI Lab、真实接口、异常矩阵和Tauri实机验收 |
| 大文件拆分演变成机械搬目录 | 冲突增加但维护性不改善 | 按资源所有权和完整领域边界拆分，禁止半迁移 |
| 新依赖扩大包体与维护面 | 构建、升级和审计成本上升 | 默认不引入Router、Pinia、Tailwind或大型组件库，例外先做ADR |

每个节点必须可构建、可运行、可回退，不允许长期保留无法启动的中间状态。

建议使用短期分支或小PR按责任边界合入：

- design：令牌、primitive、图标和动效；
- shell：视图注册表、导航、布局、状态栏和全局overlay；
- agent-ui：计划、活动、审批、RAG、错误和产物；

- qa：fixture、UI Lab、Vitest、Playwright、视觉、安装和证据。

同一PR不得同时修改无关后端契约和多个大型页面；共享类型、令牌和状态映射由明确责任人先合入。

## 16. 最终完成定义

`0.4.0-alpha.2` 完成不是“界面看起来更现代”，而是同时满足：

- 全局信息架构更容易理解；
- Agent状态、审批、错误和产物更清晰；
- 视觉、排版、组件和动效使用统一系统；
- 核心操作支持键盘、焦点和reduced-motion；
- `0.3.0-alpha.2` 的原有功能、公开契约和安全边界没有回退；
- 新旧UI读取相同公开DTO，关闭 `ui_v2` 不改变后端执行和数据；
- 视图、会话和窗口切换后没有残留SSE、轮询、监听器、动画和子进程；
- 1280px、Windows 125%/150%缩放和长中文/路径/日志场景可完成核心流程；
- 自动化、视觉、可访问性、性能、实机、升级和回滚证据完整；
- Alpha安装包、manifest、报告、flag和测试结果绑定同一commit；
- P0/P1为0，P2有明确处置；
- 后续 `0.5.0` 可信执行工作流可以直接复用新工作台的审批、Diff、活动、错误和产物组件，而无需再次重做UI；
- 完成后立即进入 `0.5.0`，不对 `0.4.0` 单独执行7–15天观察。
