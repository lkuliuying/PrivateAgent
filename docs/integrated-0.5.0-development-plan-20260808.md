## 1. 决策摘要

从本计划生效起，不再要求 `0.3.0`、`0.4.0`、`0.5.0` 每个阶段分别等待7–15天后才能继续开发。

新的发布方式是：

1. `0.3.0-alpha` 完成 Runtime、RAG、摘要和兼容链；
2. `0.4.0-alpha` 完成 UI/UX、交互、动效和全部页面迁移；
3. `0.5.0-beta` 完成可信执行工作流和整合；
4. `0.5.0-rc.1` 功能冻结后，统一进行一次14天真实使用观察；
5. 观察通过后发布唯一稳定版本 `0.5.0`。

`0.3.0` 和 `0.4.0` 在这条路线中是内部工程检查点，不发布为面向日常使用的稳定版本，也不进入正式 updater 渠道。

按原方案，三个后续版本可能累计等待21–45天；新方案只保留一次14天正式观察，理论上减少7–31天纯等待时间，同时把测试和缺陷发现前移到开发过程。

### 1.1 保留什么

取消的是“每个中间阶段按日历等待”，不是质量保障。每个开发检查点仍必须完成：

- 单元测试、集成测试和组件测试；
- Python、Vue、Rust、迁移和构建检查；
- 对应功能的安装版 smoke；
- 高风险能力的审批、验证、取消和失败关闭测试；
- 必要的故障注入；
- feature flag 和回退路径检查；
- 代码审查及文档更新。

这些门禁按分钟、小时或最多1个工作日完成，不再附加7–15天观察等待。

### 1.2 为什么这样调整

当前架构已经具备以下条件：

- Runtime、RAG、摘要和可信工具均有独立feature flag；
- 数据库迁移采用additive方式；
- 已有较完整的Python、Vue、Playwright、Rust和安装版验证链；
- compatibility telemetry可以从开发早期持续积累；
- 新UI可以通过renderer内部开关渐进迁移；
- 高风险工作流可以逐个开启并失败关闭。

因此，不需要每完成一批代码就暂停两周。更合理的方式是持续开发、持续测试、持续收集遥测，最后对完整产品做一次真实观察。

## 2. 版本与发布模型

### 2.1 新版本路线

| 检查点 | 定位 | 是否稳定发布 | 是否正式观察 |
|---|---|---:|---:|
| `0.3.0-alpha.1` | Runtime主链完成 | 否 | 否 |
| `0.3.0-alpha.2` | RAG、审批、恢复、摘要完成 | 否 | 否 |
| `0.4.0-alpha.1` | UI设计系统和新应用壳 | 否 | 否 |
| `0.4.0-alpha.2` | Agent核心UI和业务页面迁移 | 否 | 否 |
| `0.5.0-beta.1` | 可信执行工作流完成 | 否 | 否 |
| `0.5.0-beta.2` | 全功能整合和安装版硬化 | 否 | 否 |
| `0.5.0-rc.1` | 功能冻结候选 | 候选 | **是，唯一一次** |
| `0.5.0` | 正式稳定版 | 是 | 观察通过后发布 |

内部检查点可以创建Git tag和安装包供测试，但不发布到稳定GitHub Release，也不写入正式updater通道。

### 2.2 版本跳跃说明

稳定版本可以从 `0.2.1` 直接升级到 `0.5.0`。中间版本号用于说明开发阶段和变更范围，不要求每个minor版本都单独公开发布。

升级验证必须覆盖：

- `0.2.1 → 0.5.0` 覆盖安装；
- `0.2.1 → 0.5.0` updater升级；
- 全新安装 `0.5.0`；
- `0.5.0 → 0.2.1` 应用回滚时的数据兼容说明；
- 数据库只能在明确安全时降级，默认通过应用回退而不执行破坏性downgrade。

## 3. 当前开发基线

截至2026-08-08，主分支已经进入 `0.3.0` 开发：

- M0观察工具链、runner、聚合器和共享判定逻辑已经提交；
- Chat Runtime、ContextBuilder、RAG/普通模式和SSE断线收敛已经进入实现；
- MySQL断连失败关闭已有针对性修复和故障注入；
- 摘要worker的远程Provider门控、显式授权、原始消息保留和调度幂等已有测试提交；
- UI/UX全面改造计划已经形成，但尚未进入正式代码实施；
- 当前工作区除UI计划文档外无其他未提交改动。

这意味着原M0不再需要作为“停止开发直到观察结束”的前置条件。M0改为：

1. 修复观察工具本身的可信度问题；
2. 建立开发期基线；
3. 在后续开发过程中持续采集；
4. 把最终判断推迟到 `0.5.0-rc.1` 整体观察。

## 4. `0.5.0` 集成范围

### 4.1 Runtime与智能能力

- 普通聊天默认进入durable Agent Runtime；
- RAG聊天使用统一Runtime、可信引用和失败关闭；
- ContextBuilder、token预算、截断和provider usage可观测；
- SSE流式、取消、断线、续传和审批恢复完整；
- 摘要worker独立调度、失败重试、幂等和原始消息保留；
- compatibility telemetry、diagnostics和基线报告可复核；
- legacy入口保留兼容，但桌面新请求不再依赖旧planner。

### 4.2 UI/UX Workbench 2.0

- 重组一级导航和信息架构；
- 完成设计系统2.0、语义令牌和基础组件；
- 完成应用壳、路由、三栏工作台和上下文栏；
- 重构Agent计划、活动流、工具调用、审批、错误和产物；
- 完成Today、Knowledge、Projects、Tasks、Learning、Memory、Integrations、Settings、Status、Diagnostics和Backup页面迁移；
- 统一加载、空、失败、离线、重连、停止和完成状态；
- 完成动效语义、reduced-motion、键盘和WCAG AA；
- 建立UI Lab和Playwright视觉基线。

详细设计范围继续参考 `docs/v0.4.0-ui-ux-redesign-plan.md`，但其中“必须先发布0.3.0”的条件改为“Runtime公开契约冻结”。

### 4.3 可信执行工作流

`0.5.0` 只开放有边界、有验证器、有审批和可审计的工作流：

1. 文件读取和代码搜索；
2. 文件Diff与patch proposal；
3. 受限工作区内的patch应用与回读验证；
4. allowlist命令执行，带超时、取消和进程树清理；
5. allowlist HTTP/API调用，带域名、方法、大小和秘密边界；
6. 只读数据库查询，带schema/行数/超时限制；
7. 多步骤工作流，带checkpoint、审批、幂等和恢复；
8. 公开验证结果、失败原因和产物展示。

不开放：

- 无边界通用Shell；
- 任意路径写入；
- 任意外网请求；
- 任意数据库写入；
- 绕过审批或验证器的快捷入口。

### 4.4 明确延期到 `0.6.0+`

以下能力不属于本次“核心功能与UI全部完成”的定义：

- MCP OAuth和大规模第三方生产互操作；
- 无明确需求的远程Provider全面上线；
- macOS/Linux正式支持；
- Authenticode正式证书交付；
- 移动端；
- 公网多租户服务；
- 无边界自动长期记忆写入；
- 需要外部商业账号、证书或平台设备但当前无法验收的项目。

这些条件性能力不能阻塞 `0.5.0` 核心产品完成。

## 5. 开发列车

建议工期：5–8个工作日。  
对应检查点：`0.3.0-alpha.1`。

任务：

1. 完成普通聊天Runtime接管；
2. 完成ContextBuilder和输出验证接入；

6. 确认关闭单一flag即可回退。

- Chat组件和Playwright双模式测试全绿；
- 普通聊天成功、失败、取消、断线安装版smoke通过；
- 无重复消息、重复run和双执行；
- 不等待7天，门禁通过即可进入T1/T2。

建议工期：5–8个工作日。  
对应检查点：`0.3.0-alpha.2`。

任务：

1. 完成RAG Runtime和可信引用；
2. 完成审批暂停、批准、拒绝、过期和恢复；
3. 完成Ollama/MySQL中断失败关闭；

6. 完成开发期遥测报告和故障注入。

- RAG、审批、恢复、摘要测试全绿；
- Ollama和MySQL断连场景通过；

### T3：Agent核心UI与业务页面迁移

迁移顺序：

### T4：可信执行底座与首批工作流

对应检查点：`0.5.0-beta.1`。

任务：

1. 固化工具schema、capability、risk和idempotency契约；

3. 接入文件Diff/patch工作流；
4. 接入allowlist命令；

6. 完成固定结果验证器和失败关闭；

- 每个工作流独立测试、故障注入和E2E通过；
- 超时、取消后无残留子进程；
- 重试不产生重复副作用；

5. 处理性能、资源清理和兼容遥测；
6. 完成 `0.2.1 → 0.5.0` 安装升级演练。

- 完整自动化门禁全绿；
- 全新安装、覆盖安装、升级和应用回滚通过；
- 数据保留和schema一致；

### T6：RC冻结与观察准备

建议工期：3–5个工作日。  
对应检查点：`0.5.0-rc.1`。

任务：

1. 停止新增功能；
2. 统一Python、Vue、Tauri和Cargo版本；
3. 绑定Git commit、安装包、manifest和SHA-256；
4. 完成release-check、QA evidence和代码签名状态报告；
5. 验证正式观察环境、遥测、聚合器和告警；
6. 建立14天观察任务表。

- 自动化门禁100%通过；
- 安装升级和回滚通过；
- 没有未处置P0/P1；

## 6. 中间检查点的即时门禁

| 门禁 | 目标时长 | 是否阻塞下一阶段 |
|---|---:|---:|
| lint、类型、格式、静态检查 | 分钟级 | 是 |
| 单元/组件测试 | 分钟至1小时 | 是 |
| 集成和故障注入 | 1–3小时 | 是 |
| Playwright和Tauri smoke | 1–4小时 | 是 |
| 安装包、迁移和回滚smoke | 半天至1天 | 是 |
| 开发期人工体验检查 | 30–120分钟 | 是 |

开发期测试发现问题后，修复并重跑受影响门禁即可继续，不再重新计算一个新的7天窗口。

## 7. 唯一一次正式使用观察

### 7.1 观察对象

只观察冻结后的 `0.5.0-rc.1`。观察报告必须绑定：

- Git commit；
- Python/Vue/Tauri/Cargo版本；
- 数据库schema；
- 安装包SHA-256；
- feature flag快照；
- Ollama和模型版本；
- 观察起止时间。

观察期间不得增加功能，只允许修复缺陷、文案、布局和测试。

### 7.2 固定时间

- 正式观察固定14个自然日；
- 开发期已经产生的遥测用于基线对比，但不缩短14天RC观察；
- 不因为普通P2修复重新计时；
- 一般P1修复后只对受影响场景做连续72小时复核；
- 只有数据损坏、秘密泄漏、审批绕过或重复副作用这四类严重问题，修复后才重新开始完整观察。

这样既避免每个版本重复等待，也不降低真正安全问题的发布标准。

### 7.3 样本门槛

14天内至少完成：

| 样本 | 最低数量 |
|---|---:|
| 有效Agent completed run | 200 |
| 其中真实人工交互run | 50 |
| 普通聊天 | 60 |
| RAG聊天 | 40 |
| 摘要触发与复用 | 20 |
| 只读工具调用 | 20 |
| 文件Diff/patch工作流 | 15 |
| allowlist命令工作流 | 10 |
| HTTP/API工作流 | 10 |
| 只读SQL工作流 | 10 |
| 审批暂停与恢复 | 20 |
| 用户取消 | 10 |
| 断线/续传/重启恢复 | 10 |

同一个run可以同时计入多个场景，但不能把失败、取消或owner unavailable计为有效completed run。

人工使用不足时，可以用真实模型和真实安装版的场景runner补足总样本，但至少50个run必须来自人工交互，不能全部使用合成脚本。

### 7.4 故障与安装场景

观察期至少包含：

- 10次正常启动和退出；
- 2次sidecar异常终止和下次启动reconcile；
- 2次Ollama中断与恢复；
- 1次MySQL短暂中断与恢复；
- 1次覆盖安装；
- 1次updater升级；
- 1次应用回滚；
- 1次审批过期；
- 1次审批参数篡改拒绝；
- 1次命令超时和进程树清理；
- 1次RAG引用验证失败；
- 1次输出验证耗尽并失败关闭。

### 7.5 UI使用覆盖

以下页面必须在至少5个不同自然日被真实使用：

- Today；
- Agent；
- Knowledge；
- Projects/Tasks；
- Integrations；
- Settings/Status/Diagnostics。

至少覆盖：

- 1280×800、1440×900和1920×1080；
- Windows 100%、125%和150%缩放；
- 左栏展开/折叠；
- 右栏展开/抽屉；
- reduced-motion；
- 长任务、长文件名、长日志和多个产物。

### 7.6 最终通过门槛

- 数据损坏、秘密泄漏、审批绕过、重复副作用均为0；
- 没有超过10分钟无状态推进且无法取消/恢复的run；
- owner lock没有双coordinator；
- 所有正常退出窗口合法满足 `ended_at >= started_at`；
- 异常窗口能被reconcile；
- 输出验证、RAG引用和领域验证器全部失败关闭；
- 工具取消/超时后无残留子进程；
- 普通聊天、RAG和可信工作流成功率达到冻结基线；
- P0/P1为0，P2有明确处置；
- UI不存在阻断核心流程的溢出、遮挡、焦点或滚动问题；
- 完整门禁、安装升级、回滚和RC报告可复核。

## 8. 持续遥测但不持续阻塞

从现在开始持续记录：

- run状态、耗时、token和验证结果；
- RAG检索、引用、拒答和P95；
- ContextBuilder截断和预算；
- 工具执行、审批、超时、取消和残留；
- sidecar窗口、owner lock和reconcile；
- Runtime/legacy compatibility mode；
- UI错误、断线、重连和页面性能。

这些开发期数据用于发现回归和建立趋势，不作为“必须等满若干天才能继续编码”的门槛。只有RC的14天报告具有最终发布判定权。

## 9. Feature Flag与回退策略

### 9.1 开关原则

- Runtime、RAG、摘要、UI v2和每类可信工作流拥有独立开关；
- 开发阶段默认关闭新高风险能力；
- 自动化和smoke通过后在内部构建开启；
- `0.5.0-rc.1` 使用计划发布的默认值；
- 回退一个能力不要求数据库downgrade。

### 9.2 建议开关组

```text
PA_CHAT_AGENT_RUNTIME_ENABLED
PA_AGENT_RAG_TOOLS_ENABLED
PA_CONVERSATION_SUMMARY_WORKER_ENABLED
PA_UI_V2_ENABLED 或 renderer等价开关
PA_AGENT_PATCH_WORKFLOW_ENABLED
PA_AGENT_COMMAND_WORKFLOW_ENABLED
PA_AGENT_HTTP_WORKFLOW_ENABLED
PA_AGENT_SQL_READONLY_WORKFLOW_ENABLED
```

开关名称以实际实现为准，但不能用一个总开关同时开启所有高风险工作流。

### 9.3 数据库策略

- RC前迁移保持additive；
- 不在开发中删除旧列、旧表和旧事件；
- 新旧UI读取相同公开DTO；
- 最终删除legacy结构安排到 `0.6.0+` 的独立迁移；
- 备份和恢复必须在每个新增持久化结构后立即更新测试。

## 10. 多人/多AI并行方式

为减少冲突，建议按所有权并行：

| 工作流 | 主要目录 | 责任边界 |
|---|---|---|
| Runtime | `src/personal_assistant/agents`、chat/agent routes | 执行链、事件、恢复、验证 |
| UI | `apps/desktop/src` | 设计系统、页面、交互和E2E |
| 可信执行 | tools、executions、workflow adapters | 有界工具、审批、验证器 |
| QA/发布 | `scripts`、`tests`、`docs`、release evidence | 门禁、安装、观察、报告 |

协作规则：

1. 每个AI开始前读取最新主分支和本计划；
2. 不允许两个AI同时大改 `App.vue`、`api.ts` 或同一模型文件；
3. 公共DTO和事件类型先单独提交，再由前后端分别消费；
4. 每个任务提交小范围、可测试、可回退的commit；
5. 不把未完成的大重构长期留在共享工作区；
6. 计划和事实文档只由QA/路线负责人统一收口。

## 11. 建议日历安排

在Runtime、UI设计和可信执行底座部分并行的情况下：

| 周期 | 主要工作 |
|---|---|
| 第1–2周 | T0/T1 Runtime收口；并行完成UI审计和设计系统基础 |
| 第3–4周 | T2新应用壳；开始Agent核心UI |
| 第5–7周 | T3核心UI和业务页面迁移；并行T4可信执行 |
| 第8–9周 | T4/T5多步骤工作流和全功能整合 |
| 第10周 | 安装、性能、视觉、无障碍和发布硬化 |
| 第11周 | T6 RC冻结和观察准备 |
| 第12–13周 | 唯一一次14天正式使用观察 |
| 观察通过后 | 发布 `0.5.0` |

这是目标节奏，不以赶工为由跳过即时门禁。若只有一个执行者，UI页面迁移和可信执行应串行，总周期可能增加，但仍只进行一次正式观察。
