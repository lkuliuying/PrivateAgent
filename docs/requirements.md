# 私人助手 Agent · 项目需求文档

> 版本：v0.1 · 日期：2026-07-04
> 对应计划：`docs/phase1-plan.md` v0.3
> 项目定位：本地优先、隐私可控的桌面私人助手。第一阶段先完成“稳定对话 + 本地知识库问答”，后续再扩展工具调用、任务管理、多 Agent 与云端能力。

---

## 1. 背景与目标

### 1.1 背景
用户希望拥有一个运行在个人电脑上的桌面私人助手，用于学习、工作资料问答、日常知识检索和未来的自动化任务处理。项目强调本地优先，默认情况下数据、文档、会话历史均保存在用户本机。

### 1.2 产品目标
1. 提供一个可长期演进的桌面助手基础平台。
2. 第一阶段先把对话体验做稳定：多轮上下文、流式输出、历史持久化。
3. 第一阶段同时支持本地知识库：导入文档、检索资料、基于资料回答并标注来源。
4. 架构上为后续工具调用、任务管理、多 Agent、云端模型切换预留扩展空间。

### 1.3 第一阶段成功标准
第一阶段完成后，用户可以打开桌面应用，完成以下核心动作：
- 查看运行状态，确认 Ollama、MySQL、向量库、本地后端是否正常。
- 新建会话并进行流式多轮聊天。
- 关闭应用后再次打开，历史会话仍可恢复。
- 导入本地文档，等待解析与索引完成。
- 启用知识库后提问，助手能基于本地文档回答并展示来源。
- 当模型、数据库、文档导入出错时，界面给出明确提示。

## 2. 用户与使用场景

### 2.1 目标用户
| 用户 | 特征 | 关注点 |
|---|---|---|
| 个人学习者 | 有大量 PDF、Word、Markdown、TXT 资料 | 快速问资料、总结知识、保留历史 |
| 开发/技术用户 | 能接受本地模型、数据库、依赖配置 | 可控、可扩展、可调试 |
| 重隐私用户 | 不希望资料默认上传云端 | 本地存储、明确上云提示 |

### 2.2 核心使用场景
1. **普通聊天**：用户输入问题，助手流式回答，并能记住当前会话上下文。
2. **资料问答**：用户导入本地资料后，围绕资料提问，助手基于检索片段回答。
3. **历史回看**：用户切换旧会话，查看之前的对话记录，继续追问。
4. **知识库管理**：用户查看已导入文档、导入状态、切片数量、失败原因，并可删除文档。
5. **运行诊断**：用户打开状态页，知道当前模型、数据库、向量库、后端服务是否可用。

## 3. 产品范围

### 3.1 第一阶段范围
第一阶段只做一个可稳定使用的本地助手底座：
- Tauri + Vue 3 桌面客户端。
- Python FastAPI 本地后端。
- Ollama 本地模型调用。
- MySQL 业务数据存储。
- 嵌入式 ChromaDB 向量存储。
- 对话、会话历史、本地知识库、基础设置、状态检查。

### 3.2 第一阶段不做
- 不做自主 Agent 行动，例如自动执行代码、操作文件、联网搜索。
- 不做多 Agent 协作。
- 不做任务、日程、笔记管理。
- 不做多用户、权限、云同步。
- 不做完整云端模型切换，只保留 Provider 扩展接口。
- 不把正式安装包作为硬性验收，只做 Tauri + Python sidecar 打包预研。

### 3.3 后续阶段方向
| 阶段 | 方向 | 说明 |
|---|---|---|
| 第二阶段 | 工具调用与本地自动化 | 受控工具调用、授权路径、活动流、工作台 UI |
| 第三阶段 | 学习、文档与编码工作流 | 项目工作区、学习系统、文档工作台、编码补丁、多步任务 |
| 第四阶段 | 长期个人工作系统 | 长期记忆、主动复习、文档集合、可回滚工作流、Provider 与备份 |
| 第五阶段 | 安装包与分发 | Windows 安装、首启配置、自动更新、签名、发布 QA、跨平台预研 |

## 4. 功能需求

### 4.1 桌面应用框架
**目标**：用户通过桌面应用进入所有功能，而不是手动访问网页。

需求：
- 应用使用 Tauri 作为桌面壳。
- 前端使用 Vue 3 + TypeScript + Vite。
- 启动后默认进入主界面，显示聊天区、会话区、知识库/设置入口。
- 第一阶段开发模式下允许手动启动 Python 后端；后续打包预研中验证由 Tauri 启动 Python sidecar。
- 当前后端不可用时，前端必须显示清晰状态，而不是空白页。

验收：
- Tauri 桌面窗口可以启动。
- 前端能调用 `/health` 并显示后端状态。
- 后端断开时，界面显示“本地后端未连接”一类提示。

### 4.2 本地后端 API
**目标**：把 AI、RAG、存储能力封装为本机 API，供桌面端调用。

需求：
- 后端使用 FastAPI + Uvicorn。
- 提供健康检查、会话、消息、聊天流、文档、设置等 API。
- 流式对话优先使用 SSE。
- 后端应支持结构化日志，便于定位错误。
- 后端端口可配置，避免本地端口冲突。

验收：
- `GET /health` 能返回 API、Ollama、MySQL、ChromaDB 状态。
- 前端可以通过本地 API 获取会话、发送消息、接收流式回复。

### 4.3 对话助手
**目标**：用户可以进行稳定的多轮对话。

需求：
- 支持新建会话。
- 支持会话列表展示。
- 支持切换会话。
- 支持用户消息和助手消息持久化。
- 支持流式输出。
- 支持停止当前生成。
- 支持关闭应用后恢复历史会话。
- 支持自动生成会话标题：用户发出首轮消息并收到助手回复后，后端基于首轮内容生成简短标题；生成失败时回退为“新对话”。

验收：
- 用户发送消息后，助手以流式方式回答。
- 同一会话内可以连续追问，助手能利用当前上下文。
- 切换会话后，消息历史正确显示。
- 重启应用后，旧会话仍存在。
- 首轮对话后，会话列表能显示自动生成的简短标题。

### 4.4 本地知识库
**目标**：用户可以导入本地文档，并让助手基于文档回答。

需求：
- 支持导入 PDF、Word、Markdown、TXT。
- 支持查看文档列表。
- 支持查看文档状态：pending、processing、ready、failed、deleting。
- 支持展示切片数量、文件大小、导入时间、失败原因。
- 支持删除文档，并同步清理 MySQL 与 ChromaDB 数据。
- 扫描件 PDF 第一阶段不做 OCR，应明确提示“暂不支持扫描件”。

验收：
- 导入正常文档后，状态最终变为 ready。
- 导入失败时，状态变为 failed，并展示错误信息。
- 删除文档后，列表不再显示该文档，检索也不再返回该文档内容。

### 4.5 RAG 问答
**目标**：用户启用知识库后，助手能检索本地资料并基于资料回答。

需求：
- 聊天页提供“启用知识库”开关。
- 启用后，用户问题先进入检索流程。
- 检索返回 `chunk_id`，后端从 MySQL 查回切片原文。
- 回答中必须展示来源信息，至少包含文档名和片段序号。
- 当检索不到相关内容时，助手应明确说明“未在知识库中找到相关资料”，而不是编造。

验收：
- 对已导入文档提问，回答能引用文档来源。
- 对无关问题提问，助手不会强行编造知识库内容。
- 关闭知识库开关后，聊天走普通对话链路。

### 4.6 设置与状态
**目标**：用户能知道系统是否可用，并调整基础参数。

需求：
- 设置页显示当前 LLM 模型、嵌入模型、Ollama 地址、MySQL 状态、ChromaDB 状态。
- 支持设置温度、上下文长度、默认是否启用知识库。
- 第一阶段 Provider 只实现 Ollama；OpenAI/Claude 字段可在配置结构中预留，但 UI 不承诺完整切换。
- 当模型未拉取、Ollama 未启动、MySQL 未启动时，给出明确提示。

验收：
- 用户可以在状态页看到各依赖是否正常。
- 用户修改基础设置后，设置可持久化。

## 5. 数据需求

### 5.1 MySQL 数据
MySQL 存储业务数据：
- 会话：sessions。
- 消息：messages。
- 文档元数据：documents。
- 文档切片原文：doc_chunks。
- 应用设置：settings。

要求：
- 所有 schema 变更通过 Alembic 管理。
- 文档导入必须记录状态和失败原因。
- 消息必须按会话和时间可查询。
- 文档切片必须通过 `chunk_id` 与 ChromaDB 关联。

### 5.2 ChromaDB 数据
ChromaDB 只存向量和最小元数据：
- `chunk_id`。
- `doc_id`。

要求：
- 不在 ChromaDB 中存完整切片原文。
- 向量库持久化到 `data/chroma/`。
- 删除文档时必须同步删除对应向量。

### 5.3 一致性要求
- MySQL 与 ChromaDB 没有跨库事务，不允许把一致性写成“事务保证”。
- 导入和删除必须通过状态机 + 失败补偿处理。
- 失败任务应可重试。

## 6. API 需求

第一阶段 API 草案：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 获取 API、Ollama、MySQL、ChromaDB 状态 |
| GET | `/sessions` | 获取会话列表 |
| POST | `/sessions` | 新建会话 |
| GET | `/sessions/{id}/messages` | 获取会话消息 |
| POST | `/chat/stream` | SSE 流式对话 |
| GET | `/documents` | 获取文档列表 |
| POST | `/documents/import` | 导入文档 |
| DELETE | `/documents/{id}` | 删除文档 |
| GET | `/settings` | 获取设置 |
| PUT | `/settings` | 更新设置 |

API 要求：
- 错误响应必须包含可展示给用户的错误信息。
- 流式接口必须支持前端停止生成。
- 文档导入类任务必须能查询状态。

## 8. 非功能需求

### 8.1 隐私
- 默认不上传文档、会话、切片到云端。
- 后续如果启用云端模型，必须在 UI 明确提示。
- API key 不应写入代码仓库。

### 8.2 性能
- 本地 14B Q4 模型首 token 目标 < 3s。
- 普通聊天输入后应尽快出现流式反馈。
- 长文档导入允许耗时，但必须显示进度或状态。

### 8.3 稳定性
- 常见依赖未启动时不能崩溃。
- 文档导入失败不能污染已 ready 的知识库。
- 应用重启后历史会话和文档状态可恢复。

### 8.4 可维护性
- core 层不依赖 UI 和 API。
- API 层不写复杂业务逻辑。
- 前端只通过本地 API 访问后端能力。
- 数据库迁移必须可追溯。

### 8.5 可诊断性
- 后端记录结构化日志。
- 关键操作日志包含 session_id、doc_id、错误堆栈或错误码。
- 状态页能帮助用户定位是模型、数据库、向量库还是后端问题。

## 10. 已确认决策

以下问题已在第一阶段需求对齐中确认：
1. **会话标题生成**：第一阶段要做自动生成。首轮对话完成后生成简短标题；失败时回退为“新对话”。
2. **RAG 引用粒度**：第一阶段展示文档名 + 切片序号；页码、段落定位、原文高亮后续再做。
3. **重复导入处理**：使用 `content_hash` 检测重复文档，提示用户选择跳过或重新索引。
4. **知识库分组**：第一阶段不做分组；后续再加 collection / workspace 概念。
5. **依赖检测向导**：第一阶段不做完整向导；M3 先用设置/状态页覆盖，正式安装包阶段再做引导式检测。

## 11. 需求定版结论

第一阶段需求定为：

**一个 Tauri + Vue 桌面客户端，连接本地 Python FastAPI 后端；后端调用 Ollama、本机 MySQL 和嵌入式 ChromaDB，实现稳定聊天、会话历史、本地文档导入、RAG 问答、来源引用、基础设置和状态诊断。**

只要这个闭环稳定，第一阶段就算成功。后续所有 Agent、工具、任务、云端、多 Agent 能力，都建立在这个底座之上。
